# K-DOG AI 분석 병렬화 계획

버전: v1.0 · 작성: 2026-10-24 · 기준 코드: `43c0173a7071a00d9153d5a99e763003279a2ad0` · 상태: PA01~PA07 기술 구현·검증·독립 cold review 조치 완료, PA07 실제 분석/리포트 1회 완료, 운영 기본값 1

## 1. 목표와 범위

한 대상의 S1 관찰 항목군을 제한된 수만큼 동시에 실행하여 AI 분석부터 리포트 발급까지의 대기 시간을 줄인다. 사용자 요청에 따라 이 폴더에는 PR 단위의 실행 계획을 작성한다. 문서 작성은 코드 구현, 유료 공급자 재실행, 운영 설정 변경 또는 병합 완료를 뜻하지 않는다.

2026-10-24 실제 사례에서 관찰 43개 항목군과 계산·애착·게시를 포함한 AI 실행은 약 96분이었다. 이는 한 사례의 직렬 실행 관측값이며 표준 처리시간이나 정확도 기준이 아니다. `96/4=24분`은 이상적인 나눗셈일 뿐이며 성능 약속으로 사용하지 않는다. 참가자 식별정보·영상·응답·운영 DB와 실측 원장은 저장소 밖에서 보관한다.

이번 구현 대상은 **중앙 Worker 한 개가 점유한 S1 run 내부의 독립 `score_v4` 항목군**이다. 한 항목군의 여러 카메라는 기존 요청 방식대로 함께 제공한다. 후속 계산·애착 해석·게시와 별도 리포트 실행은 선행 결과를 검증한 뒤 실행한다. 새로운 촬영 세션을 생성하거나 같은 대상의 run을 복제하여 속도를 높이지 않는다.

PA01~PA06에서 여러 참가자/run 동시 실행, 다중 서버·분산 큐, 공급자 Batch API, 업로드 파일 공유 캐시, 모델/FPS/추론 수준 변경은 범위에서 제외했다. 다중 Worker를 실수로 시작했을 때 설정 상한이 무력화되지 않도록 지원 운영 형태를 강제하는 것은 포함한다. 신규 패키지는 우선 도입하지 않으며 기존 Python 3.14 계열의 표준 스레드 실행기를 후보로 삼는다.

후속 사용자 요청의 [PA07 관찰 구간·업로드 재사용](K-DOG_PR-PA07_관찰구간과업로드재사용_v1.0_20261024.md)은 창별 영상 절단과 run 내부 공유 업로드를 추가한다. 같은 자료로 전체 분석·리포트 한 번을 기존 누적 $50 상한에서 확인하며 PA06의 완료 기록과 새 실행을 구별한다.

추가 사용자 요청의 [PA08 전처리 병렬화·검증 재사용](K-DOG_PR-PA08_전처리병렬화와검증재사용_v1.0_20261024.md)은 두 파생 영상의 입력 디코딩을 공유하고, 시도 내부의 검증 identity를 재사용하며 최대 두 구간을 병렬 처리한다. 같은 기존 누적 $50 내 전체 분석/리포트 한 번으로 확인하고 관찰 규칙·기본값 1을 유지한다.

## 3. 실행 설계 결정

1. 동시성 설정 후보명은 `max_parallel_score_groups`, 허용 정수는 1~4, 초기 기본값은 1이다. bool·소수·문자열 등의 허용 여부도 명시적으로 검증하며 잘못된 요청을 조용히 보정하지 않는다. PA06 실측 전 자동 기본값 상향은 없다.
2. Coordinator 하나가 항목군을 배정한다. 최대 N개만 실행 중으로 두고 끝난 자리만 채운다. 전체 43개를 무제한 제출하지 않는다. 자식 작업은 서로의 Future를 기다리지 않는다.
3. PA01~PA06의 병렬 단위는 한 항목군의 업로드→공급자 처리→추론→검증→파일 정리다. 항목군별 카메라 업로드까지 중첩 병렬화하지 않는다. 후속 PA07은 같은 run·파일 hash·credential의 업로드를 공유하고 모든 소비자 수습 뒤 정리하는 것으로 파일 수명만 확장한다.
4. 같은 `(run_id, stage, branch_key)`의 활성 attempt는 하나만 허용한다. 생성·호출 예약·채택마다 실제 actor와 점유 token을 검사한다. 호출 예산, 최대 시도 3회, schema repair 최대 1회와 기존 재사용 검증을 유지한다.
5. 모든 관찰이 해당 회차에서 정착한 뒤 기존 `collect` 규칙으로 계산한다. `running`/`retry_wait`가 남으면 후속 계산을 시작하지 않는다. 기존 규칙에 따른 영구 실패의 결측 처리·부분 게시·`partial_failed`는 보존한다. 실패를 정상 관찰이나 전체 성공으로 바꾸지 않는다.
6. 공식 중지는 현재 API처럼 즉시 `stopped`와 token 무효화를 반영해 신규 송신·채택을 차단한다. 이것을 실행 중 HTTP 요청의 물리적 종료와 구분한다. Coordinator는 미시작 작업을 취소하고 이미 송신된 작업의 응답·사용량·정리를 수습한다. 정상 완료 판정과 다음 작업 점유는 자식 작업 수습 후 수행한다. 같은 run의 재시도가 접수되어도 이전 작업이 살아 있는 동안 새 attempt를 배정하지 않는다. 중지 후 늦은 응답은 채택하지 않으며 과금 미확인 상태를 남긴다.
7. 호출 상한과 공급자 분당 요청·토큰 한도는 다르다. 429/Retry-After 및 기존 예비키 대기 규칙을 공유 배정에 반영한다. 같은 프로젝트의 다른 키를 별도 할당량으로 간주하지 않는다. 다중 프로세스 지원을 암묵적으로 주장하지 않는다.
8. 결과는 완료 순서가 아닌 설정의 항목군 순서로 조립한다. 입력·전처리·모델·프롬프트·규칙·설정 hash, 시도별 불변 파일과 실제 행위자를 보존한다. 동시성 변경을 이유로 기존 전체 설정 hash 기반 재사용 조건을 완화하지 않는다.

2026-10-24 사용자가 운영 예비키 설정 예정임을 확인했다. 구체적 fallback 동작과 오류별 인수 기준은 [PA02 FB01~FB11](K-DOG_PR-PA02_호출예약과공유제한_v1.0_20261024.md#예비키-fallback-계약과-시험-행렬)을 따른다. 예비키는 실패 복구 수단이며 정상 요청을 두 키로 분산하는 별도 동시 처리 슬롯이 아니다.

같은 날 사용자가 실측 대상을 새 폴더로 변경하고 해당 자료의 리포트까지 완료하도록 지정했다. [PA06](K-DOG_PR-PA06_실측과운영적용_v1.0_20261024.md)의 비식별 참조 `PA06-20261024-B`를 사용한다. 실제 경로는 저장소 밖 `K-DOG_AI병렬화_실측대상_20261024.json`에 연결한다. 앞서 기록한 96분과 이전 사례의 결측 조건은 새 대상의 실측값·상태로 전용하지 않는다.

경쟁 시험은 barrier/event와 통제된 transport를 사용하여 실제 겹침을 만든다. `sleep` 기반 속도만으로 동시성을 판정하지 않는다. AI 출력은 비결정적이므로 실공급자 결과의 byte 일치를 합격 기준으로 삼지 않는다. 합성 동일 응답의 의미 일치와 실제 항목/결측/근거 차이 검토를 분리한다.

관측 지표는 실행 대기, 업로드, 공급자 파일 준비, 추론, 재시도 대기, 정리, 계산·애착·리포트, 전체 벽시계, 실제 최대 동시 요청, 예약 호출 수, 토큰, 확인된 비용과 과금 미확인 건수다. 동시 작업 시간 합을 전체 처리시간으로 보고하지 않는다. P50/P95는 표본 수와 산정 가능 여부를 함께 표시한다.

실행 기록은 [검증·실행 대장](K-DOG_AI병렬화_검증실행대장_v1.0_20261024.md)에 남긴다. 문서 작업에서는 상대 링크·대상 경로·PR 선행 관계·변경 범위·공백을 확인한다. 코드 구현 시 관련 unittest, 화면 변경 시 build/e2e, PA05에서 전체 backend와 종단 회귀를 실행한다.

계획 cold review의 발견사항·수용 근거와 수정 대응은 [Cold Review 기록](K-DOG_AI병렬화_ColdReview_v1.0_20261024.md)에 남긴다. 이번 계획 검토는 구현 인수와 구별한다.

## 6. 의존성·공식 문서 확인

2026-10-24에 [Python 3.14 concurrent.futures 공식 문서](https://docs.python.org/3.14/library/concurrent.futures.html)와 [Gemini API rate limits](https://ai.google.dev/gemini-api/docs/rate-limits)를 확인했다. 스레드 실행기는 실행 중인 요청을 Future 취소만으로 중단하지 못한다. Gemini 요청/토큰 한도는 프로젝트별이며 실제 계정 한도는 AI Studio에서 확인해야 한다.

이 작업은 문서 작성이며 라이브러리 설치·API 실행·lockfile 변경은 없다. Python 프로젝트 제약은 `>=3.14,<3.15`다. 구현 PR에서는 당시 최신 안정판·선택 버전·호환성·변경점·공식 릴리스/레지스트리 링크를 다시 확인해 기록한다. 문서 버전 표시를 설치 가능한 최신 릴리스의 확인으로 대신하지 않는다. 기존 잠금 의존성은 필요한 변경이 없는 한 유지한다.

## 7. 적용과 되돌리기

신규 실행부터 선택한 동시성을 snapshot에 고정한다. 진행 중 run과 기존 결과를 덮어쓰지 않는다. 운영 문제가 발생하면 신규 기본 설정을 1로 되돌리고 기존 실행은 공식 중지·정리·재시도 경로로 수습한다. 설정 hash가 달라지는 새 run 간 재사용은 기존 검증이 허용할 때만 가능하다. DB 상태 수동 수정이나 이미 발급한 최종 결과 교체는 되돌리기 수단으로 사용하지 않는다.

코드 이전 버전으로 복귀하려면 새 설정·DB 구조를 읽을 수 있는지 먼저 확인한다. 지원되지 않으면 새 코드에서 동시성 1을 사용하는 것을 우선한다. 파괴적 DB downgrade는 계획에 포함하지 않는다.

2026-10-24 실제 실행 범위 조정: 사용자 지시에 따라 동일 PA06-B의 진행 중 N1-R1 전체 분석→리포트 발급·검수 1회를 완료한다. 원래 반복 비교 계획은 기록으로 남기며 실제 N2/N3/N4 가속 승인과 구분한다. 기본값 1 유지. 상세는 PA06의 사용자 범위 조정 기록을 따른다.
