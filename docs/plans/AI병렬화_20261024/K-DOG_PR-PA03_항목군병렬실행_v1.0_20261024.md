# K-DOG PR-PA03 항목군 병렬 실행

버전: v1.0 · 2026-10-24 · 상태: 구현·검증·독립 cold review 완료, 병합 준비 · 선행: PA02

상위: [병렬화 계획](K-DOG_AI병렬화계획_v1.0_20261024.md) · 이전: [PA02](K-DOG_PR-PA02_호출예약과공유제한_v1.0_20261024.md) · 다음: [PA04](K-DOG_PR-PA04_운영설정과진행표시_v1.0_20261024.md) · 추적: AP02·AP04·AP05

## 목표

한 run 안의 독립 관찰 항목군을 최대 N개 동시에 처리하고, 기존 계산·애착·발급 결과의 출처와 실패 의미를 유지한다.

## 구현 범위

- 변경 중심은 `run_v4.process`와 `scoring_ai_v4.handler/collect`, 공유 경계는 `Worker.stage`다. 수정 전 callers로 report/attachment 경로와 시험 영향 범위를 확인한다.
- 표준 `ThreadPoolExecutor` 기반의 작은 실행기를 우선 검토한다. Coordinator가 배정과 결과 회수를 담당하며 N개를 넘게 활성 작업을 만들지 않는다. 같은 pool 안에서 자식 Future를 기다리는 설계는 금지한다. N=1은 동일 경로에서 직렬 의미를 보장한다.
- 병렬 대상은 `score_v4`다. 정책 보류/클립 없음 프로그램 결과와 검증된 명시 reuse는 공급자 송신 없이 처리하고 별도 계량한다. 관찰 항목군 수 43을 API 호출 수 43으로 가정하지 않는다.
- 각 항목군은 기존 handler·검증·불변 출력·채택 경로를 거친다. 제출한 group과 closure가 섞이지 않게 고정하고 모든 Future 예외를 수집한다. 응답 완료 순서와 관계없이 설정 순서로 관찰/메모/사건을 조립한다.
- 관찰 작업이 전부 정착한 뒤 기존 `collect`를 호출한다. 대기 중 branch가 있으면 계산·애착·게시를 진행하지 않는다. 영구 실패 항목은 기존 결측·부분 결과 규칙을 따르고 run 상태를 정확히 산출한다.
- 재시도는 기존 attempt·schema repair·retry_at 예산을 따른다. pool 내부에서 독자적으로 HTTP 재시도를 추가하지 않는다. 이미 성공한 동일 run branch는 검증 후 재사용하고 다시 송신하지 않는다.
- 중지·actor 비활성·입력 변경·token 교체를 배정 전, 송신 전, 채택 전에 확인한다. 공식 중지 API의 즉시 `stopped`·token 무효화는 유지하고 UI 응답을 HTTP 요청 종료까지 지연하지 않는다. Coordinator는 신규 배정 중단→미시작 작업 취소→실행 중 작업 수습/정리 순서로 끝낸다. 네트워크 timeout과 finally 정리가 있어야 하며 Future 취소를 송신 취소로 간주하지 않는다.
- 중지 직후 공식 재시도가 접수되어 `queued`가 되어도 기존 자식 작업이 살아 있는 동안 새 점유/attempt를 시작하지 않는다. 수습 완료 전에 다음 run을 시작하지 않는 중앙 Worker 경계를 PA02와 연결한다. 강제 종료/재시작 시에는 이전 프로세스 생존 여부·소유권을 확인하며, 서버측 종료 여부가 불명인 송신은 과금 미확인으로 남긴다. 기존 token의 응답이 새 run/step 상태를 덮어쓰지 못하게 한다.
- 정상 실행 동안 heartbeat를 유지한다. 강제 종료 후 기존 불변 attempt 복구/abandon 규칙을 적용하고, 이전 token의 늦은 응답은 채택하지 않는다. 소유권을 잃은 Worker가 새 점유자의 run/step 상태를 종료 처리하지 않게 한다.
- PA01의 병렬 설정 미지원 제한을 해제한다. benchmark의 병렬 거절은 실제 계량 검증으로 대체하며 단순 사용자 지정 라벨만으로 병렬 실측을 인정하지 않는다.

## 검증과 합격 기준

1. N=1/2/3/4에서 활성 작업 수 상한이 지켜지고, N>1에서는 통제된 지연 provider가 실제로 겹친다.
2. 뒤 항목군이 먼저 끝나도 동일 fixture의 관찰·계산·애착 입력이 직렬과 의미상 같다. 임의 완료 순서로 다회 반복한다.
3. 느린 작업·retry_wait·영구 실패가 섞일 때 후속 단계가 조기 시작하지 않는다. 기존 부분 결과 상태가 유지된다.
4. 실행 중 중지/입력 변경/권한 상실/점유 교체 시 추가 송신과 잘못된 채택이 없고, 시작된 요청의 사용량·정리 상태가 남는다.
5. 성공 branch+중단 branch 혼합 후 재시작 시 성공분 호출 증가 0, 미완료분만 규정대로 재시도한다.
6. 예상하지 못한 작업 예외도 누락 없이 수습하며 다른 thread가 살아 있는 동안 run을 정상 종료하지 않는다.
7. provider 응답을 barrier로 붙잡은 상태에서 중지→즉시 재시도를 호출한다. 중지 응답은 즉시 반환되고, 기존 작업 수습 전 새 송신 0·이전 응답 채택 0을 확인한 뒤 재시도가 정상 진행되어야 한다.

검증은 synthetic provider 중심으로 수행하고 실영상 반복 호출은 PA06에서 한다. 초기 기본 동시성은 계속 1이다. 성능 숫자로 schema·근거·누락값 검증을 완화하지 않는다.

## 2026-10-24 구현 기록

- PA02 병합 `173bd83` 기준, 브랜치 `veluga/pa03-bounded-score-execution`. `run_v4.process`의 coordinator는 최대 N개 Future만 배정하고 끝난 자리만 채운다. N=1도 같은 경로다. `score_v4`만 병렬이며 후속 단계는 직렬이다. Future 오류 후 새 배정을 멈추고 미시작 취소·전체 drain 뒤 예외를 전파한다.
- running/retry_wait 관찰이 있으면 계산·애착·게시로 넘어가지 않는다. 영구 실패는 기존 collect의 null/partial_failed 의미를 유지한다. collect는 기존 설정 순서를 보존한다. PA01의 N=2~4 저장/실행 제한을 해제했으며 기본값은 1이다.
- 즉시 중지/token 무효화와 이전 자식 drain 전 새 once 거절을 시험했다. 예기치 않은 RuntimeError는 자식 수습 뒤 기존 crash/recovery 계약대로 전파한다. 성공 branch는 다음 회차에서 검증만 하고 재호출하지 않는다.
- 실제 Gemini 요청의 프로세스 clock ID별 업로드/추론 구간과 요청 전체 구간을 기록한다. 늦은 성공/실패/중지의 usage는 동일 attempt에 보존하며 상태·출력 채택은 변경하지 않는다. benchmark는 설정 N과 실제 요청 최대 겹침을 별도로 산출하고, 병렬 라벨에는 실제 겹침을 요구한다. 계량 누락/부분 실패는 새 모드의 성공 속도 통계에서 제외한다.
- 실제 S1 handler의 N=1/N=4 합성 관찰·계산 의미 일치, N=1~4 상한·겹침·후속 장벽·중지/재시도·예외 drain을 확인했다. 독립 리뷰와 정확한 명령·결과는 실행 대장 참조. 실공급자 성능·운영 적용은 PA06이며 이번 외부 호출은 0회다.
