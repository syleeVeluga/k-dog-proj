# K-DOG PR-PA02 호출 예약과 공유 제한

버전: v1.0 · 2026-10-24 · 상태: 구현·검증·독립 cold review 완료, 병합 준비 · 선행: PA01

상위: [병렬화 계획](K-DOG_AI병렬화계획_v1.0_20261024.md) · 이전: [PA01](K-DOG_PR-PA01_실행계약과측정_v1.0_20261024.md) · 다음: [PA03](K-DOG_PR-PA03_항목군병렬실행_v1.0_20261024.md) · 추적: AP02·AP03·AP06·AP09

## 목표

여러 항목군이 동시에 진입해도 중복 attempt·예산 초과·키 전환 경쟁·중복 Worker로 인한 제한 우회가 발생하지 않도록 기반을 보강한다. 실제 스케줄링은 직렬로 유지한다.

## 구현 범위

- 주요 조사 지점: `worker.py`의 `stage/reserve_call/fail`, `analysis.py`의 `owned_write/claim/guard/adopt`, `storage.py`의 `Store.connect`, `gemini_keys.py`, `gemini_v4.py`, Worker 시작·종료 경로. 각 변경 심벌의 callers를 먼저 확인한다. 공유 Worker를 사용하는 report/attachment 실행에도 회귀를 적용한다.
- 현재 호출 예약은 `BEGIN IMMEDIATE` 구간에서 예산을 확인한다. 이 성질을 유지하고 마지막 예산 슬롯에 여러 작업이 도달하는 시험을 먼저 만든다. 네트워크 요청 동안 트랜잭션을 열어두지 않는다.
- `stage`의 이전 시도 읽기와 새 시도 INSERT 사이 경쟁을 검토한다. 쓰기 트랜잭션 안에서 최신 attempt·상태·점유를 재확인하여 한 branch의 활성 attempt가 하나가 되게 한다. 필요한 경우에만 인덱스/제약을 추가하며 기존 이력을 삭제해 제약을 맞추지 않는다.
- DB 연결·파일 handle·응답/usage dict는 요청/스레드마다 생성한다. 공유 observer/transport의 가변 상태를 점검하고 기본 구현과 시험 transport의 동시 안전성을 구별한다.
- 429/Retry-After는 해당 프로젝트를 공유하는 배정에 cooldown으로 적용한다. 프로젝트를 확정할 수 없는 키는 최소한 동일 설치 내에서 보수적으로 공유 제한한다. 계정별 한도 값을 추정·하드코딩하지 않는다. 설정 N은 동시성 제한이지 RPM/TPM 보장이 아님을 기록한다.
- 예비키 선택·실패 누적·`backup_retry_wait`는 기존 정책을 보존하며 동시에 발생한 오류가 키 전환을 반복하거나 대기를 우회하지 않게 한다. 같은 프로젝트의 키를 바꾸어 quota를 우회하지 않는다. 시작된 요청은 기존 선택 credential로 완료/정리하고 배정 전 상태를 재확인한다.
- 지원 형태는 하나의 중앙 Worker다. 기존 프로세스 중복 방지 장치의 범위를 확인하고 부족하면 data directory 단위의 단일 Worker 소유권을 강제한다. 프로세스 내부 semaphore만으로 설치 전체 제한이라고 표시하지 않는다. lease 인계 전 살아 있는 구 Worker의 송신이 겹치지 않는 운영/복구 경계를 시험한다.
- 원격 업로드 이름·정리 상태는 요청 소유로 유지한다. 다른 항목군 파일을 삭제하지 않으며 정리 실패·알 수 없는 업로드 완료 상태는 기존 복구 원장에 남긴다.

## 예비키 fallback 계약과 시험 행렬

2026-10-24 사용자 확인: 운영에서 예비키를 설정할 예정이며 병렬화 계획은 주키와 예비키를 함께 고려한다. 실제 키 등록은 기존 개발자 설정을 사용하고 이 문서에 키를 기록하지 않는다.

기준 코드 `gemini_keys.py:13-82`는 run별 마지막 credential 선택/전환 감사 사건을 읽고, 주키 실패 시 예비키 재시도를 요청한다. 병렬화 후에도 동일 run의 전환 결정은 원자적으로 단방향 적용한다. 여러 주키 요청의 늦은 실패가 전환 상태·대기 만료를 반복 초기화하지 않게 한다. 전환 상태는 완료 순서가 아닌 검증된 run 상태에서 읽고 재시작 후에도 유지한다.

| ID | 조건 | 계획상 동작·필수 검증 |
| --- | --- | --- |
| FB01 | 주키 미등록·삭제·파일 없음·복호화 실패·복원 후 복구 필요 | 기존 정책에 따라 송신 전에 예비키 선택. 예비키도 불가하면 명시 오류와 예약 이력 유지. 실제 송신 0회를 호출 예약 0회와 혼동하지 않음 |
| FB02 | 주키 업로드/파일 처리/추론 중 401·402·403, `400/API_KEY_INVALID` | 예산 안에서 예비키 재시도. 다른 400 오류 전체를 키 오류로 취급하지 않음 |
| FB03 | 주키 429, 500·502·503·504, 연결 소실·원격 파일 처리 timeout | 기존 전환 대상 유지. cooldown/재시도 시각과 예산 적용 후 예비키 시도. timeout 이후 원 요청 과금 가능성은 보존 |
| FB04 | schema 불일치·불완전 JSON·근거/입력 hash 오류·관찰량 검증 실패 | 오류별 기존 수리/실패 정책 적용. 키를 바꾸면 해결된다고 간주해 fallback 범위를 확대하지 않음 |
| FB05 | 주키 요청 여러 개가 동시에 실패 | 하나의 run 전환 결정, 주키로 새 요청 배정 금지, 예비키 요청도 전체 N과 호출 예산 안에서 실행. 키마다 N개씩 실행하지 않음 |
| FB06 | 전환 시 이미 송신된 주키 요청 존재 | 원 credential로 완료·정리. 결과가 유효하고 actor/token/input 검사를 통과하면 정상 채택 가능. 성공 결과를 취소하고 예비키로 중복 호출하지 않음 |
| FB07 | 예비키 없음·무효·권한/결제 오류·quota·서비스 장애 | `backup_unavailable` 등 원인 표시, 해당 오류의 기존 재시도 한도 적용. 같은 run에서 주키로 자동 왕복하거나 제3키를 찾지 않음. 예비키도 성공을 보장하지 않음 |
| FB08 | attempt 3회 또는 run 호출 예산 소진 | fallback도 같은 예산을 소비. `attempt_limit`/`call_limit`으로 종료하고 예산을 초기화하지 않음. 성공 항목군은 유지 |
| FB09 | 실행 중 키 교체·삭제, 중지·권한 상실·재시작·백업 복원 | 이미 시작한 요청의 credential reference/사용량/정리 소유 보존. 새 attempt는 현행 정책으로 키 재확인. 기존 원격 파일을 다른 프로젝트 키로 정리하지 않음. 원 credential 사용 불가 시 정리 미완료를 기록 |
| FB10 | 주키/예비키가 같은 프로젝트 또는 다른 프로젝트 | 같은 프로젝트는 quota 공유. 다른 프로젝트임이 확인되어도 동시성·run 예산은 공유하며 해당 프로젝트의 제한을 준수. 프로젝트 관계 불명 시 보수적 공유 대기. 관계를 키 문자열로 추정하지 않음 |
| FB11 | 관찰→애착→별도 report run, 공식 재시도·새 run | 같은 run의 예비키 선택은 후속 provider 단계까지 일관되게 유지. 별도 run은 기존 초기 키 선택 정책으로 시작하고 필요하면 자체 fallback. 이전 run 전환을 전역 키 교체로 전파하지 않음 |

예비키를 정상 요청의 부하 분산에 사용하거나 동일 항목군을 양쪽 키에 동시에 보내는 방식은 포함하지 않는다. 연결 소실 후 공급자 측 완료 여부를 알 수 없는 요청의 정확히 한 번 실행을 보장한다고 표현하지 않는다. 앱의 중복 배정을 막되 허용된 재시도의 과금 미확인 이력은 남긴다.

## 검증과 합격 기준

| 경쟁/장애 | 기대 결과 |
| --- | --- |
| 예산 잔여 1에서 4개 동시 예약 | 예약 성공 1개, 실제 송신도 최대 1개 |
| 같은 branch 2개 동시 시작 | 활성 attempt 1개, 중복 송신 0 |
| 서로 다른 branch 동시 저장 | 결과/usage/파일 소유가 섞이지 않음 |
| primary 오류·429 동시 발생 | 대기/키 전환 일관, 재시도·예산 상한 유지 |
| cooldown 중 새 작업 배정 | 외부 요청 시작 없음, 대기 중지 가능 |
| 같은 data directory로 Worker 추가 시작 | 지원 단일 Worker 경계를 넘지 않음 |
| 업로드 중 실패·DELETE 실패 | 원래 credential 참조로 정리 추적, 실패 은폐 없음 |

barrier로 경쟁 시점을 맞추고 실제 송신 횟수를 transport에서 검증한다. S1·report·attachment의 기존 예산/재시도/행위자/점유 시험을 수행한다. 합격 후 PA03이 사용할 배정 전 검사·예약·cooldown·종료 경계를 기록한다. 범용 분산 limiter나 큐 시스템은 추가하지 않는다.

## 2026-10-24 구현 기록

- PA01 병합 `2b4ffdb` 기준, `veluga/pa02-call-reservation-limits`. 같은 token의 running attempt는 복구하지 않는다. 이전 token의 불변 출력 복구와 신규 INSERT의 경쟁은 최신 step ID·status·token 재확인으로 차단한다. 호출 예산은 기존 `BEGIN IMMEDIATE` 예약을 유지한다.
- 429 `gemini.cooldown`은 프로젝트 관계를 알 수 없는 키를 포함해 설치 전체에 공유한다. `wait_for_provider`는 거래 밖에서 대기·중지를 검사하고 `reserve_call`이 쓰기 fence 안에서 다시 확인한다. 동시성은 RPM/TPM 보장이 아니다. quota를 키 교체로 우회하지 않는다.
- run별 예비키 전환 결정은 한번만 감사 기록하며, 늦은 primary 실패는 최초 fallback 재시도 시각을 유지한다. 이미 선택한 요청의 credential과 요청별 업로드/정리 원장은 기존 경로를 유지한다. FB01~FB04·FB07~FB11 기존 회귀와 FB05 경쟁을 검증했다. 실제 키/프로젝트 접근은 PA06 대기다.
- 중앙 Worker의 `once()`가 data directory의 OS 파일잠금 `worker-execution`을 결과 수습까지 보유한다. 기존 CLI의 프로세스 수명 `worker` 잠금도 유지한다. 네트워크 중 DB 거래를 보유하지 않는다. 프로세스 강제종료/복원 통합은 PA05에서 보강한다.
- 독립 subagent 2명 검토에서 cooldown TOCTOU와 동시 recovery 재호출을 수용 수정했다. 재현 경쟁 시험을 추가했다. 정확한 검증·리뷰·PR는 실행 대장을 따른다. 기본 직렬 유지, 새 의존성/DB 열 없음.
