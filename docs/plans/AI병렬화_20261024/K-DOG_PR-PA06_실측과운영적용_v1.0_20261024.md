## 목표

동일 조건에서 직렬·2·3·4개 동시 실행을 비교하여 사용자 대기시간 개선과 운영상 비용을 확인하고, 근거가 있는 기본값을 선택한다. 24분 또는 4배 향상을 미리 합격값으로 정하지 않는다.

2026-10-24 사용자 변경 지시로 **새 지정 자료 `PA06-20261024-B`를 사용하여 실제 최종 리포트 발급·검수까지 완료**한다. 실제 원본 경로와 파일 목록은 저장소 밖 사용자 지정 Downloads의 `K-DOG_AI병렬화_실측대상_20261024.json`에 기록한다. 이전 약 96분 사례를 이번 실측 입력으로 사용하지 않는다.

## 실측 준비

- 고정할 항목: 코드 commit, 원입력 revision/hash, 전처리 batch/clip hash, 카메라 구성·유효 관찰창, 모델·API·프롬프트·FPS·해상도·추론/출력 한도, 호출/재시도 예산. 비교 변수는 동시성 N으로 제한한다.
- PA01~PA03 계량을 사용하는 `scripts/benchmark_s1.py`의 병렬 증거 검증과 결과 출력을 완성한다. 선언한 N만 기록하지 않고 실제 작업/추론 시작·종료·최대 겹침을 기록한다. 기록 없는 실행은 실측 불충분으로 표시한다.
- 실제 계정의 프로젝트별 요청/토큰/지출 제한과 사용량 여유를 확인한다. 키 값은 보고서·로그에 남기지 않는다. 다른 작업의 API 사용량이 섞이면 함께 기록하거나 비교 시점을 분리한다.
- 주키·예비키 각각의 기존 연결 확인, 실제 선택 가능 여부, 모델 접근, 프로젝트 관계를 확인한다(AP09). fallback 발생 run은 전환 사유·슬롯별 사용량·대기시간을 기록하고, 전환 없는 속도 비교와 구분한다. 실제 429/결제 실패를 만들려고 quota를 소진하거나 운영 키를 무효화하지 않는다. 장애 행렬은 PA05에서 재현하고 실제 전환 미관측은 그대로 기록한다.
- 새 지정 폴더에서 `segments.csv`, 카메라 영상 4개, `session.json`, 진단 CSV와 녹화 로그의 존재를 확인했다. 실제 실행 전 원본 inventory/hash를 고정하고 CSV 구간, 영상 길이·음성 유무·동기화, 실제 설문 유무를 검증한다. 로그/진단 자료를 설문 응답으로 간주하지 않는다. 이전 사례의 무음·설문 미제출·걷기 국면 미확정 상태를 새 자료에 복사하지 않는다. 새 자료에서 확인한 결측·불확실성만 근거와 함께 보존한다.
- 새 대상/회차의 입력을 공식 경로로 연결하고 비교 run별 입력·전처리·설정·결과의 대응을 기록한다. 기존 대상과 이미 발급한 최종본은 보존한다. 이 자료는 성능/기술 검증 자료이며 독립 사람 정답으로 사용하지 않는다.
- PA01의 새 병렬 비교 판본/모드를 사용한다. 실제 전처리에서 채택한 카메라 개수·구간을 고정하고 4개가 채택되더라도 기존 도구의 1/3개 조건에 맞추려고 임의로 제외하지 않는다. N별 반복 식별자를 구분하고 동일 run을 여러 표본으로 집계하지 않는다.
- 같은 대상의 반복 실측을 새 참가자·독립 사람 제출로 등록하지 않는다. 실측 리포트 요청은 `cumulative=false`, `comparison=None`, `external_comparison=None`으로 고정해 다른 사례·외부 기준 자동 연결을 제외한다. 각 final 고정 사유와 실측 원장에 시험 반복임을 기록하며, 새 독립 정답이나 집단 표본으로 자동 채택하지 않는다. 연구 export가 필요하면 명시 선택과 기존 독립성 검증을 따른다. 전달용 run은 검증된 결과 중 선정 이유를 기록하며 점수가 유리하다는 이유로 선택하지 않는다.
- 비교 호출 수·예상 사용량·비용 상한·중단 조건을 먼저 적는다. 이번 계획 작성 요청만으로 유료 반복 실험을 실행하지 않는다. 실제 실행 시점의 사용자 지시와 기존 허용 범위를 확인하며 새로운 불필요한 승인 절차를 만들지 않는다.

## 실험 순서와 기록

1. 새 지정 자료의 원본 확인→입력/촬영 구간 등록→전처리→AI 분석→계산·애착→최종본 고정→리포트 발급 순으로 진행한다. 동일 배포 후보와 이 자료로 N=1 기준을 새로 측정한다. 기존 96분은 다른 사례의 참고 이력이며 대조군으로 사용하지 않는다.
2. N=2로 소규모 예비 실측한다. 중복 송신·판본 오류·정리 오류가 있으면 즉시 수습하고 원인 PR에서 수정한다.
3. 계정 한도와 안정성이 허용하면 N=3, N=4를 측정한다. 429/시간초과가 늘면 더 높은 N 실행을 멈추고 원인과 미실측 사유를 적는다.
4. 유망한 N과 N=1을 각각 최소 3회 비교하는 것을 목표로 하되 실행 예산이 부족하면 관측 수와 잠정 상태를 명시한다. 순서는 교차 배치하여 시간대 편향을 줄인다. cold/reuse 조건은 분리하고 새 모델 분석 비교에 이전 성공 branch를 섞지 않는다.
5. 각 run에서 전체 벽시계, AI 구간, 후속 리포트 발급, 업로드/추론/정리·대기, 실제 동시성, 예약/실제 송신/재시도 수, 토큰, 확인 비용·과금 미확인 건수를 보고한다. 3회 자료로 신뢰할 수 있는 P95를 주장하지 않는다.
6. 원자료 항목별 값·결측·근거 구간·최종 유형·서술 차이를 검토한다. 동일 fixture는 의미 일치가 필수다. 실제 모델의 차이는 검토 사유이며 사람 정답 없는 자료의 일치를 정확도라고 부르지 않는다.
7. 전체 처리시간 비교에 포함하는 각 run은 해당 AI 결과에 연결된 최종본 고정과 실제 HTML/PDF 발급까지 수행한다. AI만 끝난 run은 AI 구간 실측으로만 표시하고 PDF까지 완료한 표본 수에 포함하지 않는다. 공유한 입력/전처리 준비시간과 각 run의 AI 시작→PDF 발급 시간을 분리하여 기록하며, 전처리 재사용을 매번 수행한 것처럼 합산하지 않는다.
8. 최종 전달용 run을 명시적으로 선정하고 입력→AI run→최종 revision→report run의 연결과 출력 hash를 확인한다. HTML 열람, PDF 전체 페이지 렌더링·가독성·내용 검수, 원본 hash 재확인, 주키/예비키 사용·실패/재시도·과금 미확인 기록까지 마친다. 중간 문제가 발생하면 원인 수정→관련 재검증→공식 재시도/새 실행을 거쳐 완료한다. 실패 이력과 이전 불변 결과를 덮어쓰지 않는다.
9. 모든 시작 run의 성공/부분 실패/실패/중지와 실패까지 시간을 남긴다. 속도 비교의 유효 성공 표본은 같은 입력·채택 관찰 범위·후속 단계 완료 조건을 충족해야 하며, provider 오류로 관찰이 빠진 빠른 `partial_failed` run을 성공 표본으로 취급하지 않는다. 정책 보류·원본 결측과 기술 실패를 분리한다. 재시도 대기를 포함한 전체 벽시계와 실패율을 함께 제시하고, 조건별 성공 표본 수가 부족하면 성능 결론은 잠정으로 남긴다.

## 필수 전달물과 완료 기준

- 지정 새 자료로 생성한 최종 HTML·PDF와 실제 앱의 발급 manifest. 출력 파일과 참가자 상세는 저장소 밖 결과 폴더에 보관한다.
- 전 과정 실행 보고서: 원본 확인, 입력/전처리, 분석, 최종 고정, 리포트 발급·검수의 실제 상태·시간·실패 및 수정 내역.
- 실측 원장: source 참조, 입력·전처리 hash, 코드/설정, 동시성별 반복 수, run/final/report 연결, 사용량·fallback·정리 상태·산출물 hash. 저장소에는 비식별 요약만 남긴다.
- AP08은 속도 표 작성만으로 완료하지 않는다. 지정 자료의 전달용 리포트가 실제 발급되고 검수되어야 한다. 발급이 막히면 원인·남은 조건을 명시하고 리포트 완료는 미완료로 유지한다. 자료 부족으로 판단을 보류하는 것과 발급 실패를 구분한다.

## 운영 결정 기준

안전 인수 AP01~AP07과 AP09의 자동 장애 검증은 모두 통과해야 한다. AP09의 실제 키 연결/접근 확인과 실제 전환 관측 여부는 별도로 기록한다. 이후 직렬 대비 AI 구간 중앙값 30% 이상 단축을 **잠정 성능 목표**로 두고, 실제 총 대기시간 개선·재시도/제한 오류·비용·결과 차이를 함께 비교한다. 목표에 못 미치거나 변동성이 크면 기본값을 올리지 않고 측정 결과와 병목을 기록한다. 30%는 고객 SLA나 확정 성능 보장이 아니다.

N=4가 N=3보다 빠르지 않거나 오류/비용이 증가하면 더 작은 N을 선택한다. 인원 간 동시 처리량은 이번 실험에서 측정하지 않으므로 사람/시간 수치로 환산하여 운영 보장하지 않는다. 업로드 공유 등 추가 최적화가 필요하면 근거를 남기고 별도 후속 범위로 제안한다.

성공 run의 중앙값이 빨라도 실패·부분 실패·미발급 비율이 증가하면 기본값 상향 근거로 인정하지 않는다. 비교군별 성공 표본 목표 미달 또는 오류 증가 원인이 미해결이면 기본값 1을 유지한다. 특정 N이 불안정하면 그 결과를 공개한 채 충분한 표본과 검증을 갖춘 더 작은 N을 검토한다.

## 배포와 되돌리기

기본값 상향을 선택하면 새 개발자 설정 판본으로 신규 run부터 적용한다. 현재 run·이전 설정·최종 결과를 덮어쓰지 않는다. `docs/DEVELOPMENT.md`와 `docs/PILOT_OPERATIONS.md`에 지원 중앙 Worker 수, 동시성 설정, 제한 대기, 중지·복구·되돌리기 절차를 반영한다.

운영 중 오류 증가 시 신규 기본값을 1로 복귀하고 활성 run은 공식 중지·정리 경로로 처리한다. 기존 성공 branch 재사용은 설정 hash 등 현행 조건에 따른다. 코드 downgrade보다 동일 코드의 직렬 설정을 우선한다. 필요한 배포물의 commit/hash와 설치 검증 근거를 남긴다.

완료 상태는 `기술 구현 완료 / 실측 완료 / 운영 기본값 결정 / 운영 적용`으로 각각 기록한다. 자료·예산·계정 한도가 부족하면 해당 단계만 대기로 남기며 성능을 꾸며 완료 처리하지 않는다.

## 2026-10-24 구현과 실제 측정 준비 기록

- 선행 PA05 [PR #155](https://github.com/syleeVeluga/k-dog-proj/pull/155) 병합 `c48d52d`에서 `veluga/pa06-measurements-operations`를 시작했다. PA05 제품 후보 `e9a1529`의 backend/frontend/resources 실행 코드와 달라지는 부분은 없다. 이번 코드는 읽기 전용 benchmark와 관련 시험이며 운영 안내를 보완한다.
- `benchmark-clock-20261024-pa06`은 AI 요청→실제 PDF 발급을 측정하고 공유 입력/전처리 준비시간은 별도 필드에 둔다. 기존 clock/S16은 수신 시작→PDF 계약을 유지한다. scope를 섞지 않고, PDF 벽시계 `n`과 AI 구간 `ai_n`을 구별하며 중앙값을 제공한다. provider request 전체와 inference의 실제 겹침을 clock별로 각각 집계한다.
- 독립 subagent 2명이 기존 S16에 AI-only 시각을 넣어 유효 표본으로 집계할 수 있는 P2와 AI 표본 수 누락을 발견했다. 기존 S16의 scope 혼입을 명시 거절하고 `ai_n`을 별도로 노출했다. 독립 재검토 추가 결함 없음. 기존 28개와 신규 5개 회귀를 확인하며 결과를 실행 대장에 기록한다.
