# K-DOG 영상 자동 구간과 자동 분석 계획

버전: v1.0 · 2026-10-23 · 기준: `main / 36816cf` · S1.1 · 상태: 1단계 실측 완료 ([실측 결과](#실측-결과)), 2단계 설계를 자막 기반으로 확정, 구현 대기

## 배경과 결정

현재 흐름은 「영상 파일 업로드」 → 「촬영 기록 (8구간)」에서 절차 근거·8구간 시각 입력(또는 구간 CSV 가져오기)·확정 → 「전처리」 명시 실행 → 「독립 채점」에서 「AI 분석 시작」 명시 실행이다. 사람 조작이 4단계이고, 녹화 도구 CSV가 없으면 8구간 시각을 손으로 넣어야 한다.

2026-10-23 사용자 결정:

| 항목 | 결정 |
| --- | --- |
| 기본 흐름 | **영상만 올리면** AI가 8구간 **초안**을 만들고 전처리·AI 채점 준비까지 자동으로 진행한다. 사람은 「확정」 한 번만 누른다. |
| 기존 과정 | 그대로 둔다. 자동 흐름은 **별도 메뉴**로 추가하고, 기존 촬영 기록·전처리·독립 채점 화면과 서버 계약은 바꾸지 않는다. |
| 검토 없는 자동 확정 | 1단계 실측 결과를 보고 교수님이 허용할 때 켜는 **개발자 설정**으로 둔다. 기본은 꺼짐. |
| 순서 | ① 실측(실제 Gemini 호출, 소량 비용) → ② 결과를 보고 구현. 이 문서는 ①의 절차와 ②의 설계를 함께 적고, ①의 결과로 ②를 확정한다. |

범위 밖: 채점 규칙·관찰창·산식 변경, 녹화 도구 수정, 걷기 6국면·사건·관찰 근거의 자동 생성(별도 결정), 퇴장 끝을 예정 길이로 채우기(실제 시각 요구에 어긋남).

## 1단계 실측 (스파이크)

목적: AI가 전체 회차 영상에서 찾은 8구간 시작 시각이 녹화 도구 CSV와 몇 초나 다른지 잰다. 이 수치가 ②의 설계(초안으로만 쓸지, 자동 확정을 허용할지, 어느 카메라를 기준으로 할지)를 정한다.

- 도구: [`scripts/segment_boundary_spike.py`](../../scripts/segment_boundary_spike.py). 영상 한 개를 통째로 한 번 올려 8구간 시작 시각·단서·확신도를 JSON 스키마로 받고, 같은 카메라의 `CAMk_영상초`와 비교한다. MKV는 FFmpeg로 재다중화(재인코딩 없음)해 MP4로 보낸다. 원격 파일은 호출 뒤 삭제한다. 키는 등록된 Gemini 주키를 앱 함수로 읽고 어디에도 출력하지 않는다. 앱 DB에는 쓰지 않는다.
- 정답: [`segments.csv`](확정%20영상%20및%20구분_20261014/segments.csv) (2026-10-14 회차, 8구간 시작, CAM1~CAM4 영상초).
- 입력: 같은 회차의 `5_2_CAM1_복도정면.mkv`~`5_2_CAM4_참여자_오른쪽.mkv` (약 335초, 오디오 없음). `.mkv`는 저장소 제외 대상이라 같은 폴더에 두어도 커밋되지 않는다(2026-10-23 수령).
- 추가 도구: [`scripts/overlay_boundary_spike.py`](../../scripts/overlay_boundary_spike.py). Gemini 응답 단서에서 발견한 녹화 자막을 공급자 호출 없이 읽어 같은 비교를 한다.
- 실행 (backend/, 키를 등록한 Windows 사용자):

  ```powershell
  uv run --locked python -X utf8 ../scripts/segment_boundary_spike.py --csv "../docs/plans/확정 영상 및 구분_20261014/segments.csv" --video CAM1 "<폴더>/6_CAM1_복도-정면.mkv" --video CAM2 "<폴더>/6_CAM2_테스트룸-입구.mkv" --repeat 2 --report "D:/tmp/segment-spike.json"
  ```

  CAM1(복도·입장/퇴장)과 CAM2(방 입구·혼자/재회/낯선 사람)를 먼저 재고, 필요하면 CAM3·CAM4를 더한다. `--repeat 2`로 같은 영상의 편차를 본다. `--dry-run`은 호출 없이 변환·대조 경로만 확인한다(2026-10-23 로컬 MP4로 통과).
- 비용·시간: 영상당 업로드 1회 + `gemini-3.8-flash` 호출 1회, 1 fps 정적 처리. 호출 수는 영상 수 × 반복 수이며 보고서 JSON에 토큰·시간을 남긴다.
- 판정 기준(사전 고정):

  | 결과 | ②의 설계 |
  | --- | --- |
  | 8구간 모두 찾고 평균 오차 ≤ 2초, 최대 ≤ 5초 | 초안 자동 생성 + 사람 확정. 자동 확정 설정 후보. |
  | 찾았지만 오차가 그보다 큼 | 초안 자동 생성 + 사람 확정(시각을 반드시 손봄). 자동 확정 설정은 넣지 않음. |
  | 구간을 자주 놓치거나 카메라에 따라 크게 다름 | 자동 구간은 보류. 대안: 업로드할 때 CSV를 함께 올리면 자동으로 읽어 확정까지 진행. |

- 기록: 결과 JSON의 요약(구간별 오차·놓친 구간·토큰·시간)을 이 문서의 「실측 결과」 절에 옮기고 원본 JSON은 저장소 밖에 둔다. 교수님 확인은 별도다.

## 실측 결과

2026-10-23, 5_2 회차(2026-10-14 15:07 촬영) CAM1~CAM4 MKV(각 335.2~335.3초, H.264 1080p 30fps, 오디오 없음)와 같은 회차의 `segments.csv`. 영상 4개는 저장소 밖(`.mkv` 제외)에 있고 CSV만 커밋되어 있다.

### Gemini 추정 (`segment_boundary_spike.py`, 실제 호출 4건)

`gemini-3.8-flash`, 1 fps 정적, 영상당 업로드 1회(155~168초, 원격 처리 57~64초), 추론 65~78초, 호출당 입력 22,418 토큰·출력 0.5~1.1k·사고 1.8~2.3k.

| 영상 | 회차 | 찾은 구간 | 평균 오차 | 최대 오차 | 2초 이내 |
| --- | --- | --- | --- | --- | --- |
| CAM1 복도 | 1 | 2/8 | 6.5초 | 11.3초 | 1 |
| CAM1 복도 | 2 | 2/8 | 17.9초 | 24.4초 | 0 |
| CAM2 방 입구 | 1 | 8/8 | 12.1초 | 41.1초 | 4 |
| CAM2 방 입구 | 2 | 8/8 | 3.0초 | 14.4초 | 7 |

- CAM1은 방 안이 보이지 않아 2~7구간을 찾지 못한다(올바른 거절). CAM2는 같은 영상·같은 설정에서 두 회차가 12.1초/3.0초로 크게 달라 재현성이 없다.
- 퇴장은 두 회차 모두 −14.4초다. 모델은 보호자가 실제로 나가는 순간을 잡고, CSV는 운영자가 버튼을 누른 시각이라 **정의 자체가 다르다**.
- CAM2 2회차가 7/8을 1.6초 안에 맞춘 이유는 응답 단서에 적힌 대로 **화면 좌상단 자막을 읽었기 때문**이다. 1회차는 자막을 쓰지 않았다.
- 판정: 사전 기준의 셋째 행(놓치거나 카메라·회차에 따라 크게 다름). **AI 추정으로 구간을 만들지 않는다.**

### 자막 전환 읽기 (`overlay_boundary_spike.py`, 공급자 호출 0건)

녹화 도구가 모든 카메라 영상에 두 줄 자막을 새긴다: `CAMk 이름 | 참가번호 5_2 | 벽시계`, `경과 hh:mm:ss | N. 구간이름 (구간 mm:ss)`(첫 구간 전에는 `구간 표시 전`). 구간이름 칸은 운영자가 구간을 넘길 때만 바뀌므로, 1 fps로 그 칸의 흰 글자(밝기 > 235)만 이진화해 3초 이상 유지되는 변화를 전환으로 보고 30 fps로 정밀화했다. Pillow와 동봉 FFmpeg만 사용하며 영상당 약 1분이다.

| 카메라 | 전환 | 구간 경계 | CSV 대비 지연 (평균 / 범위) | 지연 보정 후 최대 오차 |
| --- | --- | --- | --- | --- |
| CAM1 | 9 (자막 등장 1 + 경계 8) | 8/8 | +1.27 / +1.22~+1.33초 | 0.06초 |
| CAM2 | 9 | 8/8 | +1.22 / +1.13~+1.27초 | 0.09초 |
| CAM3 | 9 | 8/8 | −1.23 / −3.53~+1.31초 | 2.54초 (아래 참조) |
| CAM4 | 9 | 8/8 | +1.13 / +1.07~+1.27초 | 0.14초 |

- 거짓 전환 0건(초기 임계 180에서는 자막 띠 뒤로 사람이 지나갈 때 11건이 섞였고, 235로 올리자 사라졌다).
- 자막은 버튼 누름보다 **일정하게 약 1.1~1.3초 늦게** 바뀐다(도구가 1초 단위로 갱신). 상수를 빼면 CAM1·2·4는 0.15초 안에 CSV와 일치한다.
- **CAM3 발견:** 자막의 「경과」 시계를 영상 시간과 비교하면 CAM1은 9개 지점 모두 일치하지만 CAM3는 t=50에서 +1초, t=100~200에서 +4초, t=300에서 **+8초** 앞서다가 t=330에서 0으로 돌아온다. 프레임 수(10,055 vs 10,059)·타임스탬프 간격(50ms 초과 0건)은 정상이므로 캡처 단계에서 내용이 끊기고 PTS만 이어진 것이다. 따라서 CSV의 `CAM3_영상초`(CAM1 대비 고정 −0.048초 가정)는 이 카메라에서 **최대 8초 틀리고**, 프레임에 새겨진 자막이 유일하게 맞는 값이다. 이 사실은 방금 병합된 CSV 기반 입력([최종 CSV 촬영 입력 개선](K-DOG_최종CSV촬영입력개선_v1.0_20261023.md))에도 해당하므로 녹화 도구 담당자에게 CAM3 캡처 끊김을 알리고, 앱은 카메라별 경계를 **각 영상의 자막에서 직접** 읽어야 한다.
- 판정: 사전 기준의 첫 행을 넘는다(보정 후 0.15초). **2단계는 자막 전환 읽기로 구간을 만들고, 검토 없는 자동 확정을 설정 후보로 둔다.**

## 2단계 구현 설계 (실측으로 확정)

새 메뉴 「분석·평가 → 자동 분석」(가칭). 기존 메뉴와 서버 계약은 유지하고, 새 흐름은 기존 API를 순서대로 호출하는 **오케스트레이션**으로 만든다. 새 저장 형식을 만들지 않는다. 구간 경계는 Gemini가 아니라 **녹화 자막 전환**에서 읽는다.

1. **구간 초안(새 worker 단계 `caption_segments_v4`)**: 영상 연결이 끝난 회차에서 연결된 **모든 카메라 영상 각각**의 자막 전환을 읽는다(실측 스크립트와 같은 방법: 1 fps 이진화 → 3초 유지 → 30 fps 정밀화). 카메라마다 자기 영상의 시각을 쓰므로 카메라 간 오프셋을 가정하지 않는다(CAM3 발견의 대응). 결과는 기존 `recording_s1`에 **초안(미확정)** 으로 저장하고 `procedure_note`에 "자막 전환 초안 · 영상 hash · 전환 시각 · 지연 보정값"을 남겨 사람이 입력한 시각과 구별한다. 구간 끝은 다음 구간 시작, 퇴장 끝은 비워 둔다(현행 CSV와 같음). 전환이 8개가 아니거나 자막이 없으면 초안을 만들지 않고 사유를 남긴다(기존 CSV·수동 입력으로 진행).
2. **지연 보정**: 자막은 버튼 누름보다 약 1.2초 늦다. 초안 시각을 "자막 전환 − 1.2초"로 둘지 "자막 전환 그대로"로 둘지는 평가 기준 결정이므로 교수님 확인 사항으로 두고, 확정 전까지는 **보정 없이 전환 시각 그대로** 저장하며 보정값을 설정으로 둔다.
3. **확정 화면**: 자동 분석 메뉴에서 8구간 초안과 각 구간 시작 전후 프레임을 보고 「확정」한다. 확정은 기존 `PUT recording-s1(confirmed=true)`이다. 수정이 필요하면 기존 촬영 기록 화면으로 간다.
4. **확정 후 자동 진행**: 확정 저장이 끝나면 서버가 전처리 실행을 **자동 접수**하고, 전처리가 끝나면 AI 분석 실행을 자동 접수한다. 둘 다 기존 요청 ID·점유·재시도 규칙을 그대로 쓰며, 자동 접수된 실행은 `requested_by: auto`로 표시한다. AI 분석 자동 접수는 개발자 설정의 활성화·예산 상한 안에서만 한다(기존 `max_ai_calls`).
5. **검토 없는 자동 확정(설정, 기본 꺼짐)**: 켜면 1의 초안을 사람 확정 없이 바로 확정 상태로 저장하고 4를 이어 간다. 확정 기록에는 예약 기록 계정이 아니라 자동 흐름을 켠 **개발자 계정**을 actor로 남긴다. 실측이 첫 행을 넘었으므로 구현 대상이며, 켜는 결정은 교수님 몫이다.
6. **표시**: 자동 분석 메뉴는 참가자별로 "영상 수신 → 구간 초안 → 확정 대기/확정 → 전처리 → AI 분석 → 결과" 단계를 보여 준다. 실패 단계는 기존 화면의 사유를 그대로 연결한다. 카메라별 경계가 1.5초 넘게 다르면(CAM3와 같은 캡처 이상) 경고를 표시한다.

### 지키는 것

- 실제 시각 기록 원칙: 자막 전환은 운영자 조작의 기록이지만 앱이 읽은 값이므로 "초안"으로 두고 출처·보정값을 남긴다. 예정 길이로 시각을 채우지 않는다.
- 명시 실행 원칙의 예외는 "확정 뒤 자동 접수"뿐이며, 새로고침·재진입·재설치로 새 실행을 만들지 않는다(기존 ES02/ES03 규칙 유지).
- 비용: 구간 초안은 로컬 처리라 공급자 호출이 없다. AI 분석 자동 접수만 기존 상한을 따른다.
- 기존 메뉴·계약·시험은 바꾸지 않는다. 새 코드는 `backend/app/caption_segments_v4.py`·`backend/app/auto_flow_v4.py`(가칭)와 `frontend/src/AutoAnalysisV4.tsx`(가칭)에 둔다.

### 검증 (성공 기준)

1. 자막이 있는 합성 영상(FFmpeg drawtext로 같은 두 줄 형식)에서 8전환을 모두 찾고 사람이 자막 띠 뒤로 지나가도 거짓 전환이 없다. 자막이 없는 영상은 초안 없이 사유를 남긴다.
2. 실제 5_2 회차 4개 영상에서 초안이 `overlay_boundary_spike.py` 결과와 같다(저장소 밖 실측, 기록만 남김).
3. 영상만 연결된 회차에서 자동 흐름을 켜면 구간 초안이 `recording_s1` 미확정 상태로 저장되고 출처 문구가 남는다. 공급자 호출 0건.
4. 「확정」 한 번으로 전처리 실행 1건과 AI 분석 실행 1건이 자동 접수되고, 새로고침·재진입에서 추가 실행이 생기지 않는다.
5. 설정이 꺼져 있으면 기존 흐름과 동일하며 자동 접수 0건이다.
6. 자동 확정 설정은 기본 꺼짐이고, 켜면 개발자 계정을 actor로 확정이 기록된다.
7. 호출 상한을 넘으면 사람 확정 단계에서 멈추고 사유를 표시한다.
8. 기존 backend·E2E 시험 통과. 실제 공급자로 1회차 종단 실행은 실행 기록에 남긴다.

- CAM3 캡처 끊김(최대 8초)의 원인과 재발 방지. 이 회차의 CAM3 CSV 값은 전처리에 쓰지 않는 것이 맞다.
