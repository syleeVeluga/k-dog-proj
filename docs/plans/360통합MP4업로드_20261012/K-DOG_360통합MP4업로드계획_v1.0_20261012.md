# K-DOG 360 통합 MP4 업로드 계획

버전: v1.0 · 2026-10-12 · 기준: `1702f2b03701ce5699d11607d5cd528306e888c5` / `veluga/video-upload-wording` · 상태: 계획 수립·독립 cold review·수용 수정/재검토 완료, 제품 구현 미착수

## 1 목표와 사용자 결정

사용자는 Insta360 Studio에서 360 영상을 합쳐 만든 MP4를 올리는 파일 업로드 옵션을 추가할 수 있도록 검토·계획·cold review를 요청했다. **통합 MP4 한 개만으로 업로드·보관·참가자/촬영 회차 등록을 완료**하는 것이 이번 기능의 기본 인수다. 원본 INSV와 부모 upload ID 등록을 선행조건으로 요구하지 않는다.

현재 설명의 ‘통합’은 Studio 등에서 외부 처리한 360 촬영 결과물이라는 범위로 잡는다. 한 촬영의 렌즈 스티칭인지, 여러 촬영 파일의 시간순 결합인지, 일반 화면으로 재구도한 파일인지는 실제 파일이 없으므로 확정하지 않는다. 두 번째 경우도 업로드·보관할 수 있지만 촬영 시각을 자동 추정하지 않는다. 실제 영상 품질과 360 직접 AI 판독 지원을 완료했다고 표시하지 않는다.

이번 360 통합 MP4 옵션의 산출물은 계획 문서다. 계획 작성 단계에서 제품 구현·운영 DB 수정·실영상 변환·유료 AI 호출·배포·PR 생성/병합은 수행하지 않았다. 사용자의 후속 지시로 이 문서를 커밋·병합해도 MP01~MP03 제품 구현 완료를 뜻하지 않는다. 기존 S1 점수·원입력·파일·불변 이력은 보호한다.

## 3 제안 계약

### 3.1 입력 종류와 출처

기존 `original`, `received_conversion`, `app_derived`의 의미와 부모 요구를 유지한다. **새 입력 종류 `external_360_mp4`**를 추가하고 UI 표시를 「360 통합 MP4 (Studio 등에서 내보낸 파일)」로 한다. 이름은 구현 전 코드/타입 충돌을 확인하며 같은 의미를 가진 기존 경로가 확인되면 재사용한다.

새 종류는 `.mp4`만 접수한다. `parents=[]`, `conversion=null`이고 업로드한 MP4 자체의 bytes·크기·SHA-256·upload ID·actor·요청 내용을 고정한다. ‘촬영 원본’ 또는 앱이 검증한 변환 계보라고 표시하지 않는다. 미등록 INSV의 부모 ID/hash를 만들지 않는다. 기존 `received_conversion`의 부모 검증을 느슨하게 푸는 방식은 제외한다.

새 종류에만 `external_processing`이라는 작은 typed 메타데이터를 둔다. `projection = flat | equirectangular | unknown`, `timeline = preserved | edited | unknown`은 실제 사용자가 고른 값으로 기록하고 기본은 unknown이다. tool_name/tool_version/note는 선택 입력이며 모르면 null이다. 표시 의미는 **사용자 제공 정보, 외부 원본 미등록**이다. 자유 JSON 설정 편집기·로컬 원본 경로 수집·모르는 버전 강제 입력을 추가하지 않는다. 이 메타데이터는 기술 출처 정보이며 승인 절차가 아니다.

`external_processing`은 기존 종류에서는 없거나 null이다. 업로드 request JSON의 정보는 **업로드 당시의 불변 사용자 선언**이고, 현재 S1 입력 manifest의 같은 정보는 **해당 입력 판본의 유효 처리 정보**다. 나중 확인/정정은 아래 §3.3의 명시 경로로 새 입력 판본에 기록한다. 원래 request JSON과 이전 manifest는 재작성하지 않는다. 새 optional null 필드가 기존 요청의 정규 JSON/hash 또는 기존 S1 batch의 compatibility hash를 바꾸지 않도록 **이 확장 필드만 출처 종류에 따라 포함**하는 직렬화를 계획한다. 전체 `exclude_none` 전환으로 기존 null 표현을 바꾸지 않는다.

### 3.2 파일별 촬영 정보

기존 원본/변환본은 현행 촬영 카메라 번호를 사용한다. 새 통합본은 UI에 「360 통합 영상」으로 표시하고 실제 카메라 번호/원본 번호를 억지로 입력시키지 않는다. 기존 `camera_id`가 필수인 계약을 전역 nullable로 넓히는 대신, 새 종류에 한해 **내부 view 식별자 `EXT360`**를 사용한다. 이는 물리 카메라 1번이나 3CAM 구성의 증명이 아니다. 서버가 이 규칙을 검증하고 `source_original_number`는 null로 보존하여 CAM1→원본1 같은 자동 대응을 적용하지 않는다.

영상의 실제 식별자는 video_id/upload_id/hash다. `EXT360` 표시를 이유로 이전 파일을 대체하거나 두 번째 파일을 자동 합치지 않는다. 하나의 MP4를 가짜 CAM1/2/3 세 영상으로 복제하지 않는다. 참가자·촬영 회차는 현재 화면 흐름대로 명시 지정하며 회차 변경·stale revision·동일 파일의 다른 출처 등록은 기존 충돌 처리로 보존한다.

### 3.3 보관과 분석 경계

| 새 통합본의 확인 내용 | 업로드·보관·등록/내려받기 | 기존 전처리·영상 분석 입력 |
| --- | --- | --- |
| 일반 화면 `flat`, 시간 연속성 `preserved` | 허용 | 촬영 8구간/기준 영상/실제 시각·offset 확정, 실제 decode·프레임/오디오·가시성 검사 후 기존 경로 사용 |
| 360 펼침 `equirectangular` | 허용 | 재구도 필요. 이번 범위에서 자동 구면 투영·시야 생성이나 직접 360 AI 판독은 제공하지 않음 |
| 배치 `unknown` | 허용 | 배치 확인 전 해당 파일의 영상 분석 입력 제한 |
| 시간 편집 `edited` 또는 `unknown` | 허용 | 시각 대응 확인 필요. 단일 offset으로 다중 절단/속도 변경을 복원하지 않음. 시간 편집 매핑 도구는 후속 범위 |
| 실제 decode 실패·프레임/음성 누락 | 완료 업로드 bytes 보존 | 기존 기술 오류/부분 가용·미관찰 사유. 원본 파일을 정상 품질로 표시하지 않음 |

Studio 사전 처리와 K-DOG의 관찰창 절단·실제 1fps·음성/가시성 검증은 별개다. `analysis_ready=false`라는 기존 업로드 응답 의미를 유지한다. 형식/시각 한계는 파일별 가용성으로 표시하고 함께 등록된 정상 영상의 유효 창까지 일괄 막지 않는다. 미지원 출처는 클립 생성/명시 재사용/영상 공급자 전송 경로에서 확인한다. 기존 `ViewWindowV4.availability='conversion_required'`와 reasons를 우선 재사용하여 새 전역 상태 머신을 만들지 않는다.

**시각의 전파도 검사한다.** edited/unknown 새 통합본을 점수용 기준 영상이나 공통 시각으로 변환되는 사건·관찰 근거·확인된 offset의 실제 시간 앵커로 확정하지 않는다. 해당 파일을 클립에서만 제외해도 그 파일의 사건창이 정상 view로 전파될 수 있기 때문이다. 미확인 offset 목록이나 값 없는 초안 참조가 있다는 이유만으로 정상 영상의 확정을 일괄 막지 않고 실제 시각 의존성을 확인한다. 초안 원기록은 보존하며 시간 유지가 확인된 기준/근거로 바꾸고 재확정하도록 안내한다. equirectangular+preserved는 투영 형식만을 이유로 시간 근거에서 제외하지 않는다. 공통 validator의 사람 채점/계산 호출자까지 검토하여 영상과 무관한 정상 업무를 일괄 차단하지 않는다.

**등록 후 처리 정보 확인/정정:** `PATCH /api/cases/{case_id}/videos/{video_id}/external-processing`를 작은 후보 API로 계획한다. session_id·expected_revision·typed external_processing를 받고 활성 업무 계정/현재 세션·대상/회차·file hash를 확인하여 **같은 video_id/upload_id/bytes를 유지한 새 S1 입력 revision**으로 저장한다. 실제 actor는 기존 store.save/changes 기록으로 남긴다. source_kind·부모·conversion·camera·원본 번호·원래 request_json/hash·link_json은 변경할 수 없다. 업로드 당시 선언과 현재 정보는 화면에서 구분하며 source snapshot의 불변 계보 검증과 고정 입력 판본의 유효 metadata 검증을 분리한다. unknown→flat/preserved 확인에 같은 파일 재업로드를 요구하지 않는다.

metadata 정정 뒤 기존 batch/실행은 당시 입력에 고정하고 현재 입력 기준 새 전처리를 명시 실행한다. 시간 근거에 쓰인 파일의 timeline 정보가 바뀌면 촬영 기록의 재검토/확정이 필요함을 표시하고 위 시간 검증을 적용한다. 기존 촬영 근거가 unknown으로 새 파일을 참조하지 않았으면 정상 근거까지 무효로 처리하지 않는다. 이미 정정된 같은 정보를 재시도할 때의 stale revision 응답과 최신 조회를 명시하며 원래 업로드의 동일 요청 반복 결과는 보존한다.

실제로 MP4를 재구도하거나 재편집하여 bytes가 바뀌면 새 파일/hash/요청으로 등록한다. 원본 계보가 앱에 등록되어 있는 새 파생본은 기존 `received_conversion` 경로를 사용한다. 같은 회차의 같은 hash에 다른 provenance를 새 업로드로 덮어쓰는 경로는 허용하지 않는다.

### 4.1 ES 선행 구현을 반영한 진행 — 2026-10-12 후속 결정

사용자 지시에 따라 **ES01 → ES02 → ES03 → MP01 → MP02 → MP03**으로 순차 진행한다. 상세 순서와 단계별 인계는 [ES 전체 계획 §4.1](../내실행과분석진행_20261012/K-DOG_내실행과분석진행표시계획_v1.0_20261012.md#41-mp-계획과-통합-진행-순서--2026-10-12-후속-결정)을 따른다. 최초 업로드 표현 정리/조사 기준 `1702f2b`는 이력이며 MP01 착수 기준은 ES03까지 병합된 실제 commit으로 갱신한다. 공통 서버/화면 파일은 선행 변경을 반영한 뒤 수정한다.

MP01은 ES01 실행 식별·원래 actor·단계 기록·결과 pointer·outdated·접수 조회를 유지하며 출처/시각 검증을 확장한다. metadata 정정은 과거 결과를 현재 입력으로 채택하지 않고, 실행 중 revision 변경은 기존 guard와 해당 시도의 실패/대체 기록으로 처리한다. MP02는 ES02의 내 목록·지정 실행 상세·폴링/문맥 보호에 새 영상 표시와 제한 사유를 연결하며 공유 최신 결과로 되돌리지 않는다. AI 상태 요약은 ES03의 선택 run_id/고정 입력 기준을 유지한다.

MP03에 조합 인수 VM-ES-T01~04(metadata 정정 후 과거 성공/outdated·실행 중 정정/지연 응답·미지원/부분 가용·직원별 원래 실행자)를 추가한다. VM-R01~08/VM-T01~08과 ES-T01~18은 유지한다. 각 단계는 관련 회귀를 수행하고 마지막 MP03에서 ES를 포함한 최종 전체 회귀/ZIP 설치를 확인한다. 기존 독립 cold review는 당시 범위의 이력이며 이번 순서 조정의 독립 재검토·제품 시험 완료를 뜻하지 않는다.

## 6 확인 대기와 범위 상한

- 실제 통합 MP4의 projection·편집 여부·코덱·오디오·Studio 버전은 미확인이다. 파일을 확보한 때 보호된 경로에서 hash와 실제 조건을 기록한다. 이 확인은 업로드 옵션 구현의 선행 차단 조건이 아니다.
- 진짜 360 파일을 직접 AI에 보내는 품질, 자동 재구도·개체 추적·시각 편집 매핑·SDK 설치·360 전용 플레이어·외부 전송/고객 발송은 이 계획에 포함하지 않는다. 필요 시 실제 파일 조사 결과로 별도 계획한다.
- 기존 raw 입력의 원본·부모 연결, S1 점수·발급본·이전 판본을 폐기/이관하지 않는다. 새 종류를 모르는 옛 앱을 같은 운영 DB에 실행하지 않으며 업데이트/복구는 호환 버전과 snapshot으로 안내한다. 새 전환 marker/승인체계는 만들지 않는다.
- 고객 원본/평가 규칙의 source 대조는 이번 문서 검토에서 재실행하지 않았다. [S1 원본 목록](../../archive/개발반영_20261003/K-DOG_원본자료목록_v1.0_20261003.md)의 과거 hash 검증을 이번 검증으로 재계수하지 않는다.

## 7 버전 확인·검토·실행 기록

계획 단계는 새 라이브러리/SDK를 설치하거나 앱 라이브러리를 실행하지 않는다. 현재 manifest의 잠금판을 기초로 하고 MP01/MP02/MP03 착수 전에 공식 릴리스·registry·API 문서로 최신/선택 버전·runtime/peer 호환·선택 이유·확인일/링크를 각각 기록한다. 관련 없는 의존성 업그레이드는 하지 않는다.

2026-10-12 외부 사실 확인: [Studio 파일 내보내기](https://onlinemanual.insta360.com/studio/en-us/operation-guide/file-management/file-export-instructions)는 MP4 등 내보내기를 설명한다. [VR 360 내보내기](https://onlinemanual.insta360.com/studio/en-us/operation-guide/file-management/instructions-for-vr-panoramic-video-editing-and-export)는 360 프로젝트 배치를 구분한다. [공식 재구도 안내](https://www.insta360.com/blog/tips/how-to-edit-and-reframe-360.html)는 360 촬영에서 일반 화면 선택을 설명한다. 이것이 K-DOG의 실제 파일 품질/직접 분석 검증은 아니다. [ffprobe 문서](https://ffmpeg.org/ffprobe.html)는 실제 스트림/컨테이너 정보 확인 근거다. Studio 최신판 번호·특정 코덱 성공·처리시간을 추정하지 않는다.

각 구현 PR는 구현 → 관련 검사 → 독립 cold review → 수용/보류/거절 기록 → 수용 수정/재검증 → 문서 → 해당 작업 지시에 따른 push/PR 순서를 적용한다. 현재 계획 자체의 검토는 [Cold Review](K-DOG_360통합MP4계획ColdReview_v1.0_20261012.md), 문서 검증은 [검증 기록](K-DOG_360통합MP4계획검증_v1.0_20261012.md)에 기록한다.

2026-10-12 독립 reviewer `cold_mp4_plan_review`의 P1/P2 2건을 수용했다. 동일 파일의 나중 metadata 확인/정정을 새 S1 입력 판본으로 저장하는 경로와, 편집/미확인 파일의 시각 근거가 정상 영상의 관찰창으로 전파되지 않도록 하는 검증을 MP01~MP03에 반영했다. 같은 reviewer의 재검토에서 두 발견의 계획 수준 해결·신규 actionable0을 확인했다. 제품 구현/시험·실제 파일 품질·배포를 완료한 것으로 기록하지 않는다.
