## 1 문제와 결과

[전처리 페이지](../../../frontend/src/pages/Preprocessing.tsx#L8)는 공통 전체 참가자/업무 단계 목록을 쓴다. [전처리 상세](../../../frontend/src/PreprocessingPanelV4.tsx#L58)는 동기 POST 완료 후에만 갱신한다. 이번 PR은 전처리 목록을 ‘내가 실행한 전처리’로 교체하고, 실행을 요청한 때부터 실제 처리 종료까지 같은 실행의 진행 상태를 보여준다.

다른 메뉴의 공통 진행 목록은 유지한다. 사용자 결정은 현재 직원의 실행 작업만 보는 것이며, 공유 참가자 선택이나 업무 접근을 제한하는 결정이 아니다.

## 2 목록과 새 실행

1. 전처리 페이지 첫 화면은 ES01 API의 내 실행 목록이다. 기존 공통 `진행 단계`, `미완료만`, 원평가자/전체 다음 할 일 열은 전처리에서 제거한다. 제목 `내가 실행한 전처리`, 필터 `전처리 상태`로 표시한다.
2. 검색은 참가자 ID·순번·반려견·보호자 표시 정보의 기존 범위와 맞추고 행사 필터를 유지한다. 상태는 `전체 / 실행 중 / 완료 / 확인 필요`다. 한 행에 참가자·반려견, 회차, 구체 상태/유효성 배지, 실행 시작 시각, 작업 버튼을 표시한다. 원래 실행 직원은 현재 로그인 직원이므로 반복 열은 두지 않는다.
3. 한 행은 한 실행이다. 과거 행을 합쳐 참가자의 최신 상태로 대체하지 않는다. 최신순으로 조회하며 `더 보기`는 ES01 cursor를 사용한다.
4. 상단 `전처리 실행`을 누르면 공유 참가자/현재 회차를 검색·선택하고 기존 설정/촬영 준비 안내를 연다. 미실행 대상도 이 경로에서 찾는다. 참가자가 없어 실행할 대상이 없는 상태와 내 실행 이력이 없는 상태를 다른 문구로 표시한다.
5. 내 기록의 `상태 확인/결과 보기/상세 보기`는 지정 execution_id·session_id를 열며, 기존 공유 최신 batch로 결과를 갈아 끼우지 않는다. 과거 회차 상세는 보존 결과를 보여주고 새 실행은 현재 회차 선택으로 명시 이동한다.
6. 촬영 확정은 실행 대상 상세에서 전처리 준비 조건으로 유지한다. 일반 상태 필터에는 넣지 않는다. 화면의 ‘운영자만 시작’처럼 현재 공통 업무권한과 어긋나는 안내를 ‘실행 버튼을 눌러 시작’으로 고친다.

## 3 시작 후 상태와 갱신

- 버튼 클릭 직후 `전처리 실행 요청 중`을 표시한다. 이중 클릭은 현재 pending 요청을 재사용한다. 서버 시작 이벤트를 확인하기 전에는 실행 중으로 확정하지 않는다.
- 실행에 사용할 request_id는 pending 요청의 입력/설정 fingerprint와 함께 보존한다. POST 처리 중에도 ES01 request_id 조회로 접수된 실행을 찾아 execution_id를 고정한다. 응답 유실 시 새 요청을 자동 생성하지 않는다. 접수됐으면 그 실행 조회를 이어가고, 접수 여부를 확인할 수 없으면 `요청 접수 여부 확인 중`과 조회 재시도를 안내한다.
- 상세의 상태는 `요청 중 → 클립 제작 → 관찰창 결과 정리 → 결과 검증·저장 → 완료/일부 완료/실패/중단`이다. 재사용은 `요청 중 → 재사용 검증 → 결과 검증·저장`으로 표시한다. 실제 기록이 없는 단계/완료율/남은 시간은 추정하지 않는다.
- 조회 주기는 활성 실행 동안 2초를 기본으로 한다. 서버 요청을 겹쳐 쌓지 않고, 종료/문맥 해제/로그아웃 시 타이머를 정리한다. 목록도 내 실행이 running일 때 갱신하며 신규 실행/POST 접수 상태에서는 목록 재조회로 실행을 찾는다. 메뉴 복귀·탭 재노출·수동 새로고침에서 상태를 재검증한다.
- 최초 로딩, 요청 제출 중, 배경 상태 조회를 분리한다. 배경 조회만으로 실행/새로고침 버튼을 반복 비활성화하지 않는다. 실제 동일 작업 실행 중의 중복 실행 제어는 유지한다.
- 일시적 네트워크/5xx 오류는 마지막 상태와 `상태 조회 연결 끊김 · 마지막 확인 시각`을 유지하고 제한된 간격으로 자동 재조회한다. 연결 실패를 처리 실패/완료로 바꾸지 않는다. 인증 해제/로그아웃은 내 목록·선택 실행·pending 요청·폴링을 비운다.
- 참가자·회차·계정이 바뀐 뒤 도착한 상태/POST 응답은 새 문맥에 적용하지 않는다. 페이지 재진입/새로고침 때 실행 조회만 수행하며 다시 POST하지 않는다. 필요한 진행 중 식별자는 계정·회차와 결합해 현재 세션 범위에만 보존한다.
- 같은 execution_id에서도 POST 완료/수동 재조회 등 상태를 확정하는 응답을 적용할 때 이전 배경 조회를 generation/sequence로 무효화한다. 완료 후 늦게 도착한 예전 running 응답이 완료를 되돌리지 않게 한다. 명시 새 실행은 별도 execution_id로 추적하며 상태를 단순히 시간순 추측하지 않는다.
- 같은 입력의 응답 미확인 재전송과 실패/중단 후 **새 요청으로 재실행**을 구분한다. 정상 완료·일부 완료·재사용 모두 원래 execution_id/result hash를 유지한다.
- 실패 상세는 사유와 `현재 입력으로 재실행` 경로를 제공한다. 현재 회차/입력·원본/촬영 준비 조건을 다시 확인한다. 이 PR에 새로운 중지 기능/큐를 추가하지 않는다.

## 5 인수 기준과 검증

- [ ] ES-T07: A/B의 같은 참가자 실행이 각 로그인 목록에만 표시된다. 계정 전환 후 이전 행/필터 응답/타이머가 남지 않고 공유 업무 직접 진입은 계속 가능하다.
- [ ] ES-T08: 빈 내 목록에서도 미실행 참가자를 선택해 실행할 수 있다. 미준비 조건은 선택 상세에만 표시되고 전처리 필터에 촬영/채점/리포트가 없다. 검색 0건과 실행 이력 0건을 구분한다.
- [ ] ES-T09: 느린 POST 동안 요청중→실제 단계가 보이며 새로고침 없이 완료/일부완료/실패/중단을 갱신한다. 실제 상태와 배지, 버튼이 일치한다. 전처리 잠금 거절은 요청 오류이며 내 대기 작업이 생기지 않는다.
- [ ] ES-T10: 응답 유실·동일 pending 클릭·일시적 조회 오류·재연결에서 실행 1건만 생성되고 마지막 상태/확인 시각이 유지된다. 실패 후 새 요청 재실행은 별도 이력이다.
- [ ] ES-T11: 메뉴 이동/새로고침/회차 전환·지연 응답·로그아웃과 로그인 교체가 다른 실행 상태/결과를 덮어쓰지 않는다. 같은 실행의 running 조회를 지연시킨 뒤 POST 완료를 적용하고 옛 조회를 반환해도 완료가 유지된다. 이전 회차/직원 결과와 현재 회차 실행을 구분한다.
- [ ] ES-T12: 1366/390px에서 상태·단계·오류/복구 안내가 기술 정보 접기 밖에 보이고 버튼/표가 잘리지 않는다. 폴링으로 포커스가 튀거나 전체 상태 문구가 매번 반복 낭독되지 않는다. 채점/리포트 목록과 공유 접근 회귀가 통과한다.
