## 문제와 결과

현장 흐름은 보통 「접수 데스크에서 참가자 등록 → 나중에 설문 응답 파일 올리기」다. 지금은 파일의 참가자 ID가 이미 접수된 ID면 「이미 등록된 ID입니다. 기존 참가자와 회차를 명시적으로 연결하세요」 오류가 나고([forms_v4.py:348-349](../../backend/app/forms_v4.py#L348-L349)), 운영자가 행마다 대상을 골라야 한다. 또 한 행이라도 오류가 있으면 파일 전체를 확정할 수 없다 (F07). 열 연결은 파일마다 처음부터 다시 한다.

이 PR 이후 (권장안 기준):

- 파일의 `(행사 ID, 참가자 ID)`가 기존 참가자와 **정확히 같으면** 미리보기에 「기존 참가자 갱신 · 0001 초코 · 1차 촬영」으로 표시하고 바뀌는 문항을 전후 값으로 보여준다. 운영자가 「기존 참가자 N명 갱신 확인」을 체크해야 확정할 수 있다.
- 오류 행이 있어도 정상 행만 등록할 수 있다. 확정 버튼은 「정상 12행 등록 · 오류 2행 제외」로 표시하고, 제외 행은 원본 값 + 오류 사유 열을 붙인 CSV로 내려받아 고친 뒤 다시 올린다.
- 열 연결 설정에 이름을 붙여 저장하고(예: 「2026 가을 신청폼」) 다음 업로드에서 불러온다. 같은 현장의 다른 PC에서도 보인다.

## 범위와 결정

- **Q01 (ID 일치 갱신)**: 매칭은 행사 ID와 참가자 ID 문자열의 정확한 일치만 쓴다. 이름·견명·보호자명·시각은 매칭에 쓰지 않는다. 현재 회차는 그 참가자의 `selected_session_id`다. 미리보기 단계에서 서버가 대상(`case_id`, `session_id`, `expected_revision`)을 고정하므로, 확정 전에 다른 요청이 참가자를 바꾸면 기존 revision 검사로 거절된다. 삭제 이력 ID 거절, 판본 불일치 거절은 그대로다.
- 미리보기 요청에 `match_existing_ids: bool`(기본 `false`)을 추가한다. 화면은 `true`로 보낸다. `false`일 때 동작은 현행과 같다 (역호환).
- 명시 대상(`targets`)이 있는 행은 명시 대상이 우선한다.
- **Q02 (부분 등록)**: 확정 요청에 `accept_partial: bool`을 추가한다. `true`면 `errors`가 있어도 정상 행만 한 트랜잭션으로 반영하고, 결과에 제외 행 번호와 사유를 그대로 돌려준다. 미리보기 hash 고정·같은 요청 반복 시 같은 결과는 유지한다. 정상 행이 0이면 거절한다.
- 오류 행 CSV는 미리보기 결과로 화면에서 만든다 (서버 추가 저장 없음). 개인정보가 담기므로 파일명에 행사 ID와 시각만 쓰고, 화면에 「현장 PC에만 보관하고 작업 후 삭제하세요」를 표시한다.
- **Q05 (연결 설정 저장)**: 서버에 `forms_mapping_presets` 테이블(이름, `FormsMappingV4`의 `columns`·`answer_labels`·`layout`·`source_profile`·`version`, 작성자, 시각)을 둔다. 불러오면 U02 자동 연결 위에 덮어쓰고, 파일에 없는 헤더는 「연결 안 됨」으로 표시한다. 삭제는 작성자·관리자. 백업은 SQLite 전체를 복사하므로([maintenance.py:162](../../backend/app/maintenance.py#L162)) 별도 변경 없이 포함되며, 복원 후 유지만 시험한다.
