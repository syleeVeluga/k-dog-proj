후속 결정(2026-10-03): 사용자는 기존 점수 등을 제거하고 전부 다시 진행해도 된다고 지시했다. 이에 기존 앱 결과의 조회·보존·이관·구판 출력 호환을 제외하고 S1에서 새로 채점한다. 원본 영상·설문·고객 검수 자료와 계정·설정·동의·삭제 이력은 유지한다. 본문의 원문 비교는 그대로 참고하되 실행 범위는 [새 전체 계획](개발반영_20261003/K-DOG_개발반영계획_v1.0_20261003.md)과 [S01 초기화 계획](개발반영_20261003/K-DOG_PR-S01_초기화와S1전환_v1.0_20261003.md)을 따른다. 실제 데이터 삭제는 실행하지 않았다.

## 1 결론과 검토 범위

**기존 기반은 재사용할 수 있지만, 이번 변경은 항목 몇 개와 리포트 디자인만 고치는 작업으로 끝나지 않는다.** 9월 29일판으로 구현된 C00~C07B의 항목 계약·촬영창·계산·AI 요청을 S1.1로 개정해야 한다. 아직 구현되지 않은 완료 의견·최종 결과·보호자 리포트는 새 기준으로 개발하고, 다중 PC 업로드·카메라 연결·360도 처리와 실자료 검증을 별도로 연결해야 한다.

가장 먼저 막아야 할 것은 **같은 항목 ID의 다른 의미를 혼용하는 것**이다. `개8·10·12·30·34`는 구점수의 숫자를 그대로 옮길 수 없다. 걷기 거리 여섯 값이 같아도 보호자 접근 예외에 따라 50%가 33.3%로 달라진다. 보호자 배점표는 같지만 최소 근거 미달 때 비율까지 보류해야 하므로 현 구현의 일부 계산도 수정 대상이다.

이번 요청의 “최종본”은 개발의 최상위 기준으로 받아들인다. 다만 **최종 문서 자체가 D01~D06, G01~G05와 일부 추가 제안을 미확정으로 명시**하므로, 이를 임의로 확정하지 않는다. 확정 규칙의 개발과 미확정 부분의 보류를 구분하면 전체 작업을 중단할 필요는 없다.

이 문서는 현재 체크아웃된 코드와 전달 자료의 정적 비교다. 다른 브랜치의 작업, 배포 서버 상태, 실제 참가자 영상의 AI 재분석은 확인 범위가 아니다. 앱 코드·기존 계획·고객 원본은 변경하지 않았다.

직접 확인한 계산 차이 두 가지는 다음과 같다.

- 거리 `[0,0,2,3,2,0]`은 현 계산에서 `3/6=50%`이다. 마지막 국면이 ‘보호자 접근’이면 S1.1은 `2/6=33.3%`여야 한다. 현재 입력 계약에는 이 예외가 없어 차이를 표현할 수 없다.
- 현 `owner_threshold([2,0,0], items=2, scenes=1)`의 순수 계산 부분은 비율 `[1,0,0]`, 유형 null을 반환한다. 최종 명세 8절의 동일한 근거 부족 조건은 **비율 미산출·판정보류**다. 현재 기본 결과 화면도 이 비율을 표시할 수 있다.

## 6 관찰 의견과 리포트

### 6.1 완료 의견과 최종 결과

영역별 최종 적용 순서는 **완료된 해당 영역 의견 → 유효한 유형 선택과 근거·작성자 → AI 기본 결과**다. 기존 C08 계획의 ‘의견이 없으면 AI’만으로는 중간의 유효 선택값을 빠뜨린다. 원점수·자동 비율·기본 유형은 보존하고 최종 해석의 출처를 별도로 기록해야 한다.

S1 의견 연결은 C31 평가자, D33~D38 여섯 영역(애착·교육태도·사람 반응·비사회적 반응·환경·성향), D39 우선 도움, B40/E40 완료 상태다. 완료에는 `B40=완료`, 평가자 존재, 여섯 영역 의견 중 하나 이상 또는 유효한 입장 선택·근거, 실제 E40 완료 판정이 필요하다. **D39만 작성하거나 B40만 완료인 경우는 완료 의견으로 적용하지 않는다.** 여섯 영역을 모두 채워야 한다는 새 조건도 넣지 않는다.

보호자 화면에는 별도 전문가 의견 상자를 추가하지 않고 같은 결과·총평·조언에 일관되게 반영한다. 연구용 독립 점수와 행사 최종 해석은 계속 분리한다. 자유 서술에서 최종 유형을 돌려주는 필드·자동 검증·실패 처리는 9절의 구현 검토안이며 D04 확정이 필요하다.

### 6.2 제공 형식에 맞춰 새로 연결할 리포트

PDF 6쪽을 모두 렌더링해 구성과 출력 형태를 확인했다. 다음 구조는 제공 견본과 포맷 안내의 기준이며, 개별 대상의 실제 유효 자료를 넣어야 한다.

| 쪽 | 구성 | 구현 시 지켜야 할 점 |
| --- | --- | --- |
| 1 | 표지와 오늘의 결과 4카드 | 교육태도·애착관계·사회성·함께걷기. 결측이어도 4개 틀 유지, 부족한 카드만 안내. |
| 2 | 기억에 남는 장면과 시간 흐름 | 유효 영상·카메라·실제 시각이 있는 장면 최대 3개. 다중 카메라의 같은 사건 중복 제거. |
| 3 | 설문 그래프 | 척도·방향·응답 수 표시. 자체 평균과 외부 비교의 사용 조건 준수. |
| 4 | 설문과 영상의 나란한 설명 | 자기보고와 영상 관찰을 같은 수치 축으로 합치지 않는다. |
| 5 | 관계·걷기 6국면·환경 및 물건 변화 | 확정된 최종 결과와 원값·조건을 사용. 미확인 물건 결과를 견본에서 복사하지 않는다. |
| 6 | 실천 제안·총평·출처 | 같은 최종 결과로 확인 가능한 강점과 도움을 연결. 실천 1~3개, 근거 부족 시 축소. |

청록색은 영상 관찰, 코랄색은 설문을 뜻하며 좋고 나쁨의 등급색이 아니다. HTML의 모바일 1열 카드 배치는 포맷 안내의 요구사항으로 확인했으며, 이번 검토에서 브라우저 반응형 동작을 실제 시험한 것은 아니다.

추가로 반영해야 할 출력 조건은 다음과 같다.

- 독립적인 ‘몸으로 본 하루’ 영역을 만들지 않는다. 몸 상태·몸털기·몸긁기·선택 꼬리는 관계·장면의 근거에 통합한다.
- 사회성의 사람·비사회적 하위영역 중 하나만 유효해도 그 부분은 출력한다.
- 기억 장면은 완료 의견이 지정한 유효 장면 우선, 다음은 전후 변화와 서로 다른 영역 우선, 중복 제거 후 동률이면 이른 시각. 1~2개는 있는 만큼, 0개는 안내로 대체한다.
- ‘찾고, 차분히 재회’는 관찰 요약이다. 네 애착 유형명이나 판정보류를 대신하는 신규 유형으로 등록하지 않는다.
- 피드백 126개는 선택 후보이며 일괄 출력 목록·완성 문장 은행이 아니다. 문장 내용과 선택 기준의 판본을 분리하고 G02 자료를 연결한다.
- 선택 유형, 카드·본문·총평·조언의 모순, 자료에 없는 사건·숫자, 결측의 0점 변환, ‘작성 필요’ 같은 내부 문구, 사람 의견을 AI 독립 판단으로 표시하는 오류를 검사한다.

기존 계획 C08~C10을 위 조건으로 개정해 구현해야 한다. 견본이 이미 제공됐으므로 별도 UI 디자인이 없어도 1차 구현의 구체적인 기준은 있다. 화면 자산·사진 추출·긴 문장·결측·인쇄 넘침·모바일 배치의 검수는 여전히 필요하다.

### 7.3 INSV와 360도 MP4

현재 업로드 API와 화면은 MP4/MOV/M4V/AVI/MKV/WEBM만 허용하므로 **INSV 직접 입력은 지원하지 않는다.** 확장자를 MP4로 바꾸는 것으로 해결되지 않는다. 변환된 MP4는 업로드 대상이지만, 360도 영상의 왜곡·피사체 크기·시선 방향 때문에 채점까지 가능하다는 보장은 별도다.

검증 순서는 INSV 원본 보존 → 공식 도구로 스티칭·내보내기 확인 → 360도 MP4와 필요한 시야를 정한 일반 MP4의 판독 비교가 적절하다. 이는 기술 검토 제안이며 아직 앱에 변환기가 구현됐다는 뜻이 아니다. [Insta360 Studio 공식 내보내기 안내](https://onlinemanual.insta360.com/onex2/en-us/studio/export)는 MP4 출력 경로를 제공한다. 실제 파일의 모델·렌즈 파일 구성·해상도·오디오·변환 후 시각 대응을 확인한 뒤 자동화 범위를 정해야 한다.

## 8 현장 운영 흐름과의 차이

| 요청 흐름 | 현재 가능한 부분 | 추가 작업 |
| --- | --- | --- |
| 카메라 1대당 PC 1대에서 확보·서버 업로드 | 인증·권한·HTTP 업로드·여러 파일 저장 기반 | 중앙 서버 접속·HTTPS/네트워크 배포·대용량 업로드 리허설. 별도 PC가 각자 로컬 서버를 켜는 방식은 중앙 통합이 아니다. |
| Google Forms 파일 업로드로 참가자 등록 | CSV/XLSX, 시트 선택, 헤더 매핑, 오류 미리보기 존재 | 현재 참가자 등록과 설문 import가 분리돼 있고 설문은 기존 참가자가 필요. 실제 폼 내보내기에서 대상 생성/기존 대상 연결/설문 반영까지 이어지는 작업 흐름과 매핑 필요. |
| 사전·현장 신청 처리 | 예약·접수·회차 모델 재사용 가능 | 같은 응답 재업로드·동명이인·중복 개 이름·응답 수정·현장 추가를 구별. 파일명·보호자 이름만으로 자동 확정하지 않음. |
| 등록된 대상에게 영상 연결 | case/session을 지정해 업로드 가능 | 영상 확보가 설문 등록보다 빠른 경우의 대기 파일·연결 흐름 필요. 현재는 등록 전 서버 업로드가 불가하므로 현장 순서를 정하거나 임시 보관 후 연결 기능을 추가. |
| 메인 PC 분석·리포트 확인 | 중앙 서버에 접속하는 실행 기반은 재사용 가능 | 다중 카메라 입력과 최종 리포트 기능이 연결돼야 완성. 운영자별 작업 상태와 중복 분석 확인 필요. |

**동시 업로드의 구체적인 충돌:** 현재 영상 등록 API는 업로드 시작과 파일 수신 완료 후 모두 `expected_revision`을 검사한다. 세 PC가 같은 참가자의 같은 revision으로 시작하면 한 업로드가 revision을 올린 뒤 다른 업로드는 409로 실패할 수 있고, 미채택 파일은 삭제된다. 화면의 직렬 업로드는 한 브라우저 안에서만 순서를 지킨다. 다중 PC 운영에서는 수신 완료 파일을 안전하게 연결하고 재시도할 수 있는 흐름이 필요하며, 단순히 revision 검사를 제거하면 기존 변경·삭제 보호가 깨진다.

제공 설문 Excel은 참가자별 열과 기본정보/문항 시트로 구성된 예비 정리표다. 현재 한 행 한 참가자·첫 행 헤더의 import에 그대로 맞지 않으며, 실제 Google Forms CSV와도 별개 형식이다. 표준화·미리보기는 필요하지만 Google Forms API 실시간 연동은 이번 요청 범위가 아니다.

근거: [import](../backend/app/intake.py), [영상 API](../backend/app/api.py), [업로드 화면](../frontend/src/VideoUpload.tsx), [서버 실행](../backend/app/manage.py). 현재도 외부 접속용 HTTPS public origin 설정을 갖추고 있으므로 ‘LAN 접속 자체가 불가능’하다고 판단한 것은 아니다. 3PC 실제 운영 검증이 남아 있다.

## 10 처리시간 질문에 대한 현재 답변

| 고객 질문 | 현재 확인 가능한 답변 |

| 3대 동시 분석 가능한가 | 현재 v3는 항목군을 순차 실행하고 각 요청의 파일 업로드도 순차다. 3대 병렬 분석은 미구현. 병렬화 가능 여부는 공급자 한도·서버 자원·호출 예산·동일 사건 통합을 포함해 검증해야 한다. |
| 원본/압축본·낮은 FPS의 시간과 결과 비교 | 비교 가능한 동일 사례 파일이 필요하다. 현재 전달 폴더만으로 실측할 수 없다. 새 리포트 실행도 미구현이므로 지금 종단 처리시간이 검증됐다고 답할 수 없다. |

현재 v3 AI 설정은 관찰창 조합별 **36개 항목군과 판정 1회, 계획상 37회 공급자 호출**을 사용한다. 이는 전체 입력이 가용한 경우의 기본 계획이며, 관찰 불가로 건너뛰는 군·재사용·재시도에 따라 실제 호출 수는 달라진다. ‘영상 하나를 한 번 요청하는 시간’을 전체 시간으로 볼 수 없다. 각 요청에서 클립을 올리는 구조여서 겹치는 클립의 반복 전송도 시간에 영향을 준다. S1 항목·창 변경과 다중 카메라 적용 후 호출 수는 다시 산정해야 한다.

근거: [AI 설정](../backend/app/settings_v3.py), [AI 실행 구성](../backend/app/scoring_ai.py), [순차 실행](../backend/app/run_v3.py), [공급자 파일 처리](../backend/app/gemini.py). 구형 worker의 병렬 실행 코드를 새 v3 3카메라 병렬 기능으로 해석하지 않았다.

후속 벤치마크는 다음 조건으로 설계하는 것이 적절하다. 이는 시험 제안이며 실시 결과가 아니다.

1. 동일 촬영의 원본과 압축본을 먼저 비교한다. 영상 길이·FPS를 유지한 압축과 FPS 감소 시험은 별도 조건으로 나눈다.
2. CAM1 단독과 3CAM 조합, INSV 변환 비용과 변환 후 MP4 분석 비용을 분리한다. 360도 MP4와 시야를 정한 일반 MP4도 구별한다.
3. 파일 해시·길이·크기·코덱·해상도·FPS·음성·카메라 offset, 서버 사양·네트워크, 앱·규칙·모델·프롬프트·샘플링 버전을 고정·기록한다.
4. 전 단계의 시작·끝·실패·재시도·호출 수·사용량과 전체 벽시계 시간을 기록한다. 캐시 재사용 여부를 분리하고 같은 조건을 반복해 변동을 보고한다.
5. 시간 외에 유효 항목 수·null 사유·사건 누락·중복·항목별 점수 차이·최종 결과 차이를 비교한다. 카메라 하나의 빠른 분석이 필요한 사건을 놓친다면 같은 품질의 대안으로 평가하지 않는다.
6. 새 리포트 기능이 연결된 뒤 업로드부터 PDF 출력까지 전체 시간을 재측정한다. 그 전에는 측정된 단계까지만 결과를 제시한다.

계속 보존할 기반은 인증·권한·동의·삭제 상태 확인, 불변 원본과 해시·revision, 실행 점유 토큰과 복구, 명시적 재사용 manifest, 판본이 고정된 결과·내보내기, 사람/AI 독립 시트다. 새 저장물이 생길 때 백업·복원·삭제 참조를 함께 연결한다.

## 14 이번 검토에서 수행한 검증과 한계

- DOCX 본문·표·변경 표시와 Excel의 원값·수식·저장 캐시를 추출해 비교했다. PDF 견본 6쪽을 렌더링하여 모두 확인했다.
- 활성 항목 수와 코드 집합, 83/4/3 구성, 수집중단33·의미변경5·신규11·명확화4·걷기 보완1을 대조했다. 보호자 배점 29개 일치, 분리 조합 25개 변경, 설문 28문항 본문 일치를 확인했다.
- 현재 코드에서 업로드·전처리·AI 호출·계산·리포트 실행 경로를 추적했다. codebase-memory-mcp 도구가 이 세션에 제공되지 않아 그 제한을 알린 후 `rg`와 직접 소스 읽기로 대체했다.
- 보호자 최소 근거 조건은 앱 전체를 구동하지 않고 해당 순수 함수의 AST를 추출해 재현했다. 걷기 예시는 현 산식과 명세 기대값을 별도 계산했다.
- 실제 공급자 호출, 참가자 영상 분석, 360도 변환, 원본/압축본 시간 측정, Excel 실제 재계산, S1 통합 인수 테스트는 수행하지 않았다. 이번 변경은 검토 문서뿐이므로 전체 앱 빌드·회귀 시험을 재실행하지 않았다.
- 분석용 산출물은 무시되는 `.codebase-memory/`에 두었다. 고객 원본과 기존 코드·계획의 내용을 변경하지 않았다.
- 최초 검토에서는 로컬 링크 존재와 검토 대상 원본27개의 해시 불변을 확인했다. 후속 계획 검수에서는 공개 저장소의 원본 제외 정책과 개발 진입점을 수정하고 Git에 포함되는 링크 대상으로 다시 검사했다. 최신 발견사항·수정·검증은 [계획 검수 결과](개발반영_20261003/K-DOG_계획검수결과_v1.0_20261003.md)에 기록한다.

PDF 읽기에는 Codex의 기존 번들 `pypdf 6.10.0`을 사용했다. 2026-10-03에 [공식 PyPI](https://pypi.org/project/pypdf/)와 [공식 6.19.0 릴리스](https://github.com/py-pdf/pypdf/releases/tag/6.19.0)에서 최신 안정판 6.19.0 및 Python 요구사항을 확인했고, 선택한 번들의 [6.10.0 텍스트 추출 API](https://pypdf.readthedocs.io/en/6.10.0/user/extract-text.html)를 확인했다. 검토용 기존 런타임을 사용하므로 앱 의존성을 설치·갱신하지 않았다. DOCX/XLSX 분석은 Python 표준 라이브러리를 사용했다.
