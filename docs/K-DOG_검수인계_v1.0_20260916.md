# K-DOG 검수 인계 — 42항목 판 P0·P1 결과물 검수를 맡는 에이전트를 위한 안내

버전 v1.0 · 2026-09-16 · 대상 커밋: `main` `9608b71` (PR #12 병합) = 시험 릴리즈 v0.2.0

이 문서는 구현을 맡지 않았던 에이전트가 저장소를 검수(코드 리뷰·문서 대조·시험 재현)할 때 **먼저 알아야 할 맥락, 지켜야 할 제약, 알려진 한계, 검수 관점**을 모은 것이다. 코드 구조 자체는 `AGENTS.md`와 `docs/DEVELOPMENT.md`가 설명하므로 여기서는 반복하지 않는다.

## 1. 검수 대상과 목적

- **대상.** 2026-09-16에 병합된 PR #1~#12. P0(PR-0~4: 카탈로그·계약·계산 v2)과 P1(PR-5~11: 입력 계약 v2, 접수·설문·촬영 메뉴, 전처리, 옛 화면 제거, 패키징·리허설).
- **목적.** 본촬영(2026-10-31~11-1)에 현장이 쓰는 P1 범위가 요구사항과 맞는지, 계산이 고객 엑셀과 일치하는지, 참가자 자료·키가 안전한지, 문서가 구현과 어긋나지 않는지 확인한다. P2(AI 채점·검수 화면·내보내기)는 아직 시작하지 않았으므로 그 부재는 결함이 아니다.
- **산출물.** 발견 사항 목록(파일:행, 심각도 bug / should-fix / nit, 한 문장 설명, 구체적 수정안)과 「확인했고 문제 없음」 목록. 파일을 직접 고치지 않는다. 수용·기각 판단과 반영은 구현 담당이 PR 본문에 기록한다.

## 3. 사용자가 내린 제품 결정 (문서보다 우선)

이 결정들은 2026-09-16에 사용자가 직접 내렸고 코드에 반영됐다. 계획 문서 초안과 다르더라도 결정이 맞다.

- **카메라 개념 없음.** 카메라 ID·역할·연결이 코드·계약·화면·문서 어디에도 없어야 한다. 한 쌍은 영상 파일 여러 개를 등록하고, 그중 하나를 8구간 시각의 「기준 영상」으로 고른다. 변경검토 §6의 「카메라 2대」 문구는 결정 이전의 표현이다.
- **설문은 CSV·Excel 가져오기로만 등록.** 화면에서 문항별 입력을 하지 않는다. `SurveyView`는 읽기 전용이다. 태블릿 자가 응답도 없다.
- **총점·등수 없음.** 설문·행동 어느 쪽에도 총점 필드가 없다(01 §6). 화면도 영역 응답 수와 유형만 보인다.
- **미정 규칙은 만들지 않는다.** 엑셀·문서로 정해지지 않은 해석은 `resources/rules/scoring-v2.json`에 데이터로 두고 고객 확인을 기다린다. 코드에 임계값을 박지 않는다.
- **우리말 라벨만.** 유형 이름은 고객 문서의 우리말(안정·불안·회피 쪽·무덤덤 등)이며 Ainsworth 용어(A/B/C형)는 계약이 거절한다.
- **대메뉴별 PR.** 화면은 접수 · 설문 · 촬영 · 자료 가져오기 · 직원 계정(+개발자)으로 나뉘고 각 메뉴가 별도 PR이었다.
- **55항목 파이프라인은 삭제하되 모듈은 P2까지 보존.** 화면·라우트는 PR-10에서 지웠고, `analysis`·`worker`·`evaluation`·`reporting`·`exports`·`developer_sample`·`app/legacy`는 `worker.py`가 import해서 남아 있다. 여기에 기능을 추가하지 않는다. 남아 있는 것 자체는 결함이 아니고, **새 코드가 이 모듈에 의존하기 시작했다면** 결함이다.

## 4. 절대 하지 말 것

- 운영 자료 폴더(`%LOCALAPPDATA%/K-DOG/data`, `KDOG_DATA_DIR`)를 열거나 그 경로로 앱·명령을 실행하지 않는다. 검수용 실행은 임시 폴더만 쓴다. `Store`는 저장소 안 경로를 거절하니 저장소 밖 임시 폴더를 만든다.
- 고객 원본 문서(`docs/최종 고객 문서/`, `resources/source/`)를 수정하지 않는다. 이관기는 원본 해시를 검사한다.
- 공급자 키·비밀번호·참가자 자료를 만들거나 출력하지 않는다. 시험 계정 비밀번호는 코드에 있는 합성 문자열만 쓴다. 공급자 연결 시험(`/api/developer/keys/{provider}/test`)은 실제 과금이 될 수 있으니 실행하지 않는다.
- GitHub 릴리즈·태그·PR 병합을 하지 않는다. 검수는 읽기와 로컬 실행까지다.
- `_to_delete/`(사용자가 수동 삭제하기로 둔 폴더)와 `releases/`(gitignore, 옛 후보 ZIP 포함)는 건드리지 않는다.

## 5. 검증 명령과 도구 함정

```powershell
# backend/에서 — 반드시 이 폴더에서 실행
uv sync --locked
uv run --locked python -X utf8 -m unittest discover -s tests          # 112개, 약 70초 (FFmpeg 필요)
uv run --locked python -X utf8 -m app.import_catalogs --check         # 원본 엑셀·PDF 대조, 파일 변경 없음
uv run --locked python -X utf8 -m app.launcher --check                # REQUIRED 파일·Python 3.14·FFmpeg
uv run --locked python -X utf8 ../scripts/rehearsal.py --pairs 3      # 합성 리허설 (72쌍은 약 3.5분)
# frontend/에서
npm ci ; npm run build ; npm run test:e2e                              # e2e 9개, 8765 포트 임시 서버
```

- `unittest discover`는 `backend/`가 현재 폴더가 아니면 `Start directory is not importable`로 실패한다. Bash에서 여러 명령을 병렬로 낼 때 작업 폴더가 공유되므로 `(cd backend && …)` 서브셸을 쓴다.
- Playwright e2e는 Git Bash에서 `uv`를 찾지 못해 서버 시작에 실패한다. **PowerShell에서** 실행한다.
- Windows 한글 출력은 `python -X utf8`이 없으면 깨진다. 모든 Python 실행에 붙인다.
- Bash heredoc으로 Python 스크립트를 넘기면 `\n`·따옴표가 깨진 사례가 있었다. 긴 스크립트는 파일로 쓰고 실행한다.
- `frontend/dist`는 gitignore 대상이라 `npm run build` 뒤에도 작업 트리는 깨끗하다. `build_release`는 깨끗한 트리를 요구한다.
- 시험은 저장소 밖 임시 폴더·합성 계정·합성 바이트만 쓴다. `tests/support.py`의 `AppCase`가 공통 준비다. FFmpeg가 없으면 전처리·리허설 시험은 skip된다(실패가 아님).

## 6. 알려진 한계·미완 (결함으로 다시 보고하지 않아도 됨)

- **계산 규칙 해석 R1~R9 고객 확인 대기.** 특히 R4·R5·R6은 문서와 엑셀 수식이 다르며 현재는 문서·라벨을 따른다. R5는 05 `3_보호자행동!K13=3`에서 발동해 동조율 invalid·SYN 제외 3개를 기대한다. `2_개행동!K25` 빈칸을 먼저 보는 03 Z6과 상태 우선순위가 다르다. R6은 J12:O12가 빈칸이라 미발동이다. R4의 접근 일관성은 J20=0 한 쌍만 값이 있고 K20:O20은 빈칸이며 다른 재료도 결측이어서 경계 전부를 골든 자료만으로 판별할 수 없다.
- **07 장비 사양 문서 미수령.** `preprocess-v1.json`의 `scale_height`·`equirect_crop`은 null이다.
- **리허설·시험은 합성 320×240 영상.** 현장 5.7K 원본의 처리 시간·용량은 미측정.
- **설치 검증은 이 Windows 호스트의 새 폴더·새 venv까지.** 깨끗한 OS·별도 PC 검증 없음.
- **worker 프로세스는 처리할 run이 없어 대기만 한다.** 실행기가 함께 띄우는 구조는 P2에서 다시 정한다.
- **개발자 설정 라우트 `/api/developer/settings/*`와 `settings.trial`은 55항목 프롬프트 구조 그대로.** 화면은 키 관리만 남겼다. `developer_sample.py`는 v1 카탈로그를 읽는다. P2 재설계 대상.
- **`usage-report`는 옛 run 기록에만 값이 있다.** 이 판에는 AI 호출이 없다.
- **`analysis_status`·`display_run_id`는 백엔드 `CaseView`에 남아 있다.** 화면은 읽지 않는다. 옛 run과 함께 P2에서 정리.
- **`intake-1.0` 자료 이관은 fixture로만 시험.** 실제 v0.1.0 운영 자료로는 미확인.

## 7. 검수 관점 제안 (우선순위 순)

1. **계산 정확성.** `app/scoring.py`가 `scoring-v2.json`과 03 엑셀 `여러쌍비교!D6:Z6` 수치 계산과 R4~R6 채택 해석의 상태 분기를 구분했는지. 골든 테스트 `tests/test_scoring_golden.py`의 기대값을 05 입력 셀·03 수식 셀·해석 번호와 직접 대조. Excel 엔진으로 수식을 재계산한 시험은 아니다. 반올림은 엑셀이 ROUND하는 자리에서만 half-up인지. R1~R9 이외의 **암묵적 해석**이 코드에 숨어 있지 않은지(있다면 규칙 파일로 빼야 함).
2. **카탈로그 이관.** `app/import_catalogs.py`가 03 엑셀 구조(4행 헤더, 9·24·9행, AD 영역코드, AY 척도)와 04 설문지(1~28, 7~9 해당 없음)를 검증하고 실패 시 멈추는지. `behavior-v2.json`의 42항목·`survey-v2.json`의 28문항이 원본과 하나하나 맞는지(특히 라벨·허용 점수·자료형).
3. **입력 계약과 저장.** `input_models.py`(`intake-2.0`)와 `frontend/src/types.ts`가 필드·리터럴 값에서 일치하는지. `storage.py` 마이그레이션(user_version 4→6)이 옛 폴더를 손상 없이 올리고 `migration_note`에 버린 응답을 기록하는지. revision 충돌(409)이 모든 쓰기 라우트에 있는지. 삭제 요청 상태가 파일 제공을 막는지.
4. **8구간·전처리.** `SessionSegments` 검증(절차 순서, 겹침 없음, 끝>시작, 영상 길이 안)이 API 경로와 전처리 경로 양쪽에서 같은 규칙인지. `preprocess.run`의 해시 검증, 불변 파일(`xb` 열기), 감사 기록이 백업·정리에 반영되는지(`maintenance.MANAGED`에 `clips`). A08 이후 `manage.py preprocess`와 API가 전처리 전용 잠금을 공유하고 런처 worker와 공존하며 정리·복원을 차단하는지.
5. **권한·안전.** 모든 `/api/cases/*` 쓰기가 `writer`(operator·admin), 읽기가 `reader`인지. 영상 파일 제공이 해시 재검증 후 인증된 사용자에게만 되는지. 키가 응답·로그·localStorage에 새지 않는지(e2e `settings.spec.ts`가 검사). 업로드 크기·확장자 제한.
6. **가져오기.** 참가자·설문 CSV/XLSX 미리보기→커밋 흐름에서 열 매핑(`ImportMapping`)이 필수 열을 강제하는지, Excel 숫자 ID를 자동 변환하지 않는지, 「해당 없음」 토큰이 7~9에만 허용되는지, 같은 답 재가져오기가 idempotent인지.
7. **문서 대조.** `PILOT_OPERATIONS.md`의 화면 라벨·명령이 `frontend/src/pages/*.tsx`·`manage.py`와 정확히 같은지. 「카메라」「동결」「55항목 화면」 같은 옛 표현이 새 문서에 남지 않았는지(`app/legacy` 설명과 변경검토의 역사 서술은 예외).
8. **시험 공백.** e2e가 XLSX 가져오기·구간 초안→확정→해제 순환·이관 메모 표시를 덮는지. 백엔드 시험이 R5·R6 무효 규칙을 합성 사례로 덮는지(`tests/test_scoring.py`). 리허설 스크립트가 실패 시 임시 폴더를 정리하는지.
9. **패키징.** `build_release.py`가 자료·키·테스트·개발 문서를 넣지 않는지(`verify_release.py` 누출 필터). `launcher.REQUIRED`가 런타임이 실제로 읽는 `resources/` 파일을 모두 포함하는지(`grep -rn "resources/" backend/app`).

## 8. 보고 형식

- 발견 사항마다: `파일:행` · 심각도(bug / should-fix / nit) · 한 문장 결함 설명 · 구체적 수정안. 재현 가능한 것은 재현 명령이나 입력 값을 함께 적는다.
- 「확인했고 문제 없음」 항목도 명시한다. 무엇을 봤는지 알아야 다음 검수가 겹치지 않는다.
- 제품 결정(3장)이나 알려진 한계(6장)에 해당하는 것은 결함으로 올리지 않되, 결정과 **구현이 어긋난** 지점은 bug로 올린다.
- 고객 확인이 필요한 새 해석 지점을 발견하면 결함이 아니라 「확인 요청 후보」로 따로 묶는다. `K-DOG_채점규칙_확인요청` 문서에 추가할 수 있게 엑셀 시트·행·칸 번호로 적는다.
- 한국어로 쓰고, 화면·문서에 나오는 용어는 그 표기를 그대로 쓴다.
