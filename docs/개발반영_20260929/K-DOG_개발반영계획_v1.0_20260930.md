## 1 목표와 적용 범위

기존 접수·원본 저장·인증·영상 처리 기반을 보존하고, 새 판본의 설문·촬영·채점·의견·리포트를 순서대로 연결한다. **기본 15개 PR(C00~C13, C07은 A/B 분리)**와 **자료 수령 후 조건부 2개 PR(C14·C15)**로 나눈다. 이 문서는 구현 계획이며 실제 브랜치·PR·앱 코드를 만들었다는 뜻이 아니다. 파일표의 ‘신설’ 경로와 계약·API 이름은 구현 제안이다.

먼저 [변경 검토 v1.1](K-DOG_개발기준변경검토_v1.1_20260930.md), 다음으로 [확인 사항과 검증 자료](K-DOG_확인사항및검증자료_v1.0_20260930.md)를 읽는다. 전체 고객 기준은 [00](../큐브전달_20260929/00_큐브_회신및개발반영기준_20260929.docx), 행동 입력·배점은 [02 원본](../큐브전달_20260929/기준자료/02_개_행동채점표_최종정리_20260929.xlsx)이다. 설문은 01, 대응은 03과 두 JSON, 촬영은 04, 판정은 07, 관찰 목적·해석 한계는 10을 함께 적용한다. 02b·02c는 보기용, 루키 HTML은 구성 참고다.

9월 13일 P0·P1·검수개선 문서는 구현 이력과 인프라 근거로 보존한다. `리포트구현/`의 PR-R01~R08은 미구현 계획이며 새 채점·판정·출력의 실행 기준으로 사용하지 않는다. 특히 ‘AI는 항상 초안이고 사람 final만 입력’, ‘유형명 금지’, ‘모든 발급에 사람 승인 필수’, ‘7개 하위영역·국내 정규분포’라는 전제를 이어받지 않는다. 자동 생성은 구현하되 실제 전달 시점·승인 정책은 확인 사항 Q09다.

## 3 단계별 사용 가능 범위와 일정

1인 개발, 기존 인프라·잠금 의존성 유지, 핵심 기준 회신, CSV/Excel 설문 입력, 로컬 HTML/인쇄·파일 전달을 전제로 한다. 각 개발일에는 해당 PR의 구현·시험·리뷰 수정이 포함된다. 고객 회신·원본 수령·정식 연구 검증 대기는 제외한다.

- **운영 전환판:** C00~C04, 약 9~14개발일(2~3주). 새 접수·설문·촬영·전처리까지 사용할 수 있다. 이 단계에도 설치 ZIP·실행·백업/복원 확인은 필요하며 C13의 해당 검사를 앞당겨 수행한다.
- **전체 구조 구현판:** 기본 15개 PR 합계 약 30~45개발일(6~9주). 실제 AI 판독이 검증되었다는 뜻은 아니다. 기존 검토의 22~30일은 큰 기능 묶음의 초안 추정이었다. 이번에는 독립 시트 UI, provider 스키마·설정·계량, 저장 참조·복구, 버전 보존과 출력 이력을 실제 PR 범위로 세분화해 다시 산정했다.
- **자료 수령 후:** C14 비교 활성화는 근거·사용 조건 확인 뒤 별도 1~2개발일이다. C15는 현행 영상과 두 전문가 독립 채점 수령 후 초기 항목별 판독·일치·비용·시간 검토에 별도 5~10개발일을 확보한다. 표본수·통계모형·수용 기준이 정해지기 전에는 정식 연구 검증의 종료일을 약속하지 않는다.

기존 10월 31일 촬영 일정은 재확인 대상이다. 유지된다면 운영 전환판과 촬영 리허설을 먼저 확보한다. 당일 최종 리포트 발급이 필요하면 자료·판정·발급 조건을 조기에 확정하고 인력·범위를 다시 산정한다.

## 4 판본과 저장 경계

새 자료의 내부 판본 이름은 `catalog-20260929-v3`, `survey-20260929-v3`, `protocol-20260929-v3` 등을 제안한다. 현재의 `*-v1.json`, `*-v2.json`을 덮어쓰지 않는다. 초기에는 새 도메인 모델·계산을 `*_v3.py`로 분리하고 판본별로 호출한다. 공통 코드 재구성은 새 기능에 필요한 만큼만 한다.

| 입력 또는 결과 | 고정할 식별자 |
| --- | --- |
| 접수·세션 | case/session ID, 입력 revision, manifest hash, 실제 촬영 절차 판본 또는 미확인 |
| 설문 | 문항 원문·척도 판본, 응답값, 명시된 빈칸 사유, 집계 정책 판본 |
| 촬영·전처리 | 원본 영상 hash, 기준 영상·실제 시각, 구간/사건 상태, batch hash, 절단/샘플링 정책 |
| 평가자별 채점 | 영상·창·항목 계약 판본, 시트 ID/revision/hash, 평가자·독립/노출 여부, 근거·사유 |
| 기본 계산·판정 | 입력 시트 ID/revision/hash, 계산 규칙, 유형·근거·반대 근거·기회·보류 사유 |
| 행사 최종 결과 | 명시적으로 선택한 기본 입력, 완료 의견 ID/revision/hash, 적용 출처·변경 사유 |
| 보호자 출력 | 최종 결과 hash, 설문·문장·비교·HTML 자산 버전, 생성 run, 이전 기준 여부 |
| 연구 내보내기 | 명시한 표본·평가자·판본·제외 사유, 시트/결과 snapshot, AI 노출·인적 수정 기록 |

입력값의 0과 빈값은 끝까지 구분한다. 채점 상태, 관찰 기회, 절차 유효성, 판정 보류는 별도 정보다. 새로운 파일 경로·표가 생기는 PR에서는 `maintenance.py` 참조 탐색·해시·백업·복원·삭제까지 함께 연결한다. 마지막 PR에 미루지 않는다.

‘가장 최근 사람 final’이나 ‘선택된 최신 AI run’을 암묵적으로 행사·연구 결과에 섞지 않는다. 동일 입력을 다시 사용하려면 명시적 reuse manifest와 판본·영상·시각·설정 hash 일치를 검증한다. 행사 의견 수정은 연구 원점수를 바꾸지 않으며 발급한 출력은 새 버전으로 재생성한다.

## 6 미확정 규칙의 처리

[확인대장](K-DOG_확인사항및검증자료_v1.0_20260930.md)의 Q01~Q12를 사용한다. 일부 불명확한 규칙 때문에 전체 구현을 중단하지 않는다. 해당 입력을 보존하고 영향받는 집계·판정·비교·전달만 보류한다. 문서에서 정한 조건은 그대로 구현하며, 임의 최소 관찰량·부분평균·정확도 문턱을 추가하지 않는다.

새 기준과 달라진 구판 R1~R9는 새 미확정 목록으로 통째 승계하지 않는다. 동의 범위·평가자 권한·최소 관찰량·초 정밀도·발급 방식은 연결되는 PR에서 회신 내용을 기록한다. 연구 비교 데이터는 근거가 없어도 구조를 만들 수 있으나 활성화할 수 없다.

## 7 공통 구현·검증 절차

한 PR 한 브랜치, 기본 접두어는 `veluga/`다. 구현 → 해당 시험·원본 대조 → 독립 cold review → 발견사항 수용/보류/거절 사유 기록 → 수용안 반영 → 재검증 → 문서 완료 표시 → 푸시·PR 생성 순서로 진행한다. 2026-09-30 사용자의 `/goal` 실행 요청에 따라 실제 브랜치·커밋·PR를 만들며, 각 PR 문서의 실행 기록으로 완료 상태를 추적한다. 실제 환경/자료가 없는 실증은 사유를 기록하고 생략할 수 있으며 합성시험을 실증으로 표시하지 않는다.

각 PR은 기존 시험을 새 판본 회귀와 함께 유지한다. 테스트 기대값은 고객 기준의 수식·행·문서에서 만들고 코드의 반환값을 복사하지 않는다. Excel 재계산값을 아직 확인하지 못한 경우 수식 해석 시험과 Excel 실대조 기록을 구분한다. 루키 예비 수치를 현행 AI 정답으로 사용하지 않는다.

```powershell
# backend/에서
uv run --locked python -X utf8 -m unittest discover -s tests -v
uv run --locked python -X utf8 -m app.import_catalogs --check
# frontend/에서, UI가 바뀐 PR
npm run build
npm run test:e2e
# 저장소 루트에서
git diff --check
```

C00에서 importer의 판본 선택 인자를 구현한 뒤 구판·신판 대조를 모두 수행한다. 전체 e2e는 PR의 UI 완료·통합 시점에 수행하며, 문서 변경만으로 앱 시험을 재실행하지 않는다. 비용이 드는 provider 검증은 합성 계약 시험과 분리하고 실제 영상·동의·검증 범위를 확보한 후 진행한다.

라이브러리·프레임워크·provider API를 실제 구현에서 사용하기 전 공식 최신 안정판·호환성·API를 온라인 확인한다. 기존 잠금 버전을 유지할 때에도 확인일·최신판·선택판·이유를 PR에 기록한다. 이번 문서 작성에는 Python 표준 라이브러리와 파일 도구만 사용했고 설치·의존성 변경이 없다.

필수 `codebase-memory-mcp`가 현재 도구 목록에 없어 한계를 알리고 직접 소스 대조로 계획을 수립했다. 후속 구현 시 도구가 제공되면 인덱스 확인·갱신과 그래프 탐색을 우선 수행한다.
