## 문제와 결과

현재 업로드는 등록된 case/session과 시작 시 revision을 요구하여 같은 참가자에 대한 3PC 동시 업로드가 충돌할 수 있다. 완전히 수신한 파일을 참가자 연결과 분리해 보존하고, 재전송 없이 안전하게 연결·재시도하는 흐름을 만든다.

근거: 운영 요청 3~4항, 통합명세 2절·D01. 인수: T01·T22의 영상 식별 기반. 카메라 동기화·판독은 S04~S08 범위다.

## 구현 순서와 상태

1. 최소 상태는 수신 중→수신 완료/실패→대상 연결이다. 서버가 발급한 upload ID와 요청 ID로 중복 요청을 구별한다. 원래 파일명은 표시용이며 저장 경로는 서버가 정한다.
2. 수신 완료 시 bytes·hash를 확정하고 불변 파일로 보존한다. 참가자 미등록이면 미연결 보관함에 둔다. 미연결 파일의 접근 주체·현장 운영 권한과 수동 정리 동작을 명시한다. 임의 보관기간을 고객 정책으로 확정하지 않는다.
3. 연결은 명시한 case/session/camera에 대해 최신 manifest를 읽고 권한·삭제·회차 존재를 검증하는 짧은 트랜잭션으로 수행한다. 기존 입력을 덮지 않는 영상 append만 처리하고 revision을 새로 발급한다.
4. 동시 연결 충돌이면 완료 파일을 삭제하지 않고 연결 재시도를 제공한다. 최신 입력을 확인한 재시도에서도 같은 receipt가 중복 영상으로 붙지 않아야 한다. 기존 revision/삭제 보호를 무조건 제거하지 않는다.
5. 원본1→CAM1, 원본3→CAM2, 원본2→CAM3을 기록한다. 카메라 목록은 D01 변경을 허용하며 같은 대상/회차의 여러 파일을 유지한다.
6. INSV는 원본 보관 대상으로 받되 분석 가능 영상으로 표시하지 않는다. 변환 MP4 연결 시 부모 INSV/관련 파일 세트, 변환 설정·도구 버전·hash를 저장하고 S05에서 읽을 수 있는지 검증한다. 확장자 변경으로 변환을 대신하지 않는다.
7. 참가자/회차 수정 후 기존 분석은 이전 입력 상태로 표시한다. 삭제 중 수신·연결·다운로드를 재검사하고 해당 대상에 연결된 원본/파생/미완료 수신물을 삭제 참조에 포함한다.
8. 실패·취소된 일부 파일은 별도 정리하며 수신 완료 후 미연결 상태와 혼동하지 않는다. 재개 가능한 청크 전송·카메라 장치 자동 제어는 이번 최소 구현에 포함하지 않는다.

## 검증과 완료 조건

- 같은 revision에서 시작한 3PC 업로드가 모두 완료 파일로 남고 한 대상에 각각 한 번 연결된다.
- 연결 중 409가 나도 파일을 다시 올리지 않고 연결만 재시도한다. 응답 유실 후 반복 요청은 중복을 만들지 않는다.
- 수신 중 네트워크 중단/디스크 부족/서버 재시작, 연결 중 대상 삭제/권한 철회/회차 변경을 시험한다.
- 동일 hash의 중복 파일과 같은 camera의 다른 촬영 파일을 구별한다. 다른 대상 자료의 존재를 중복 검사 응답으로 노출하지 않는다.
- 미연결 파일과 INSV가 채점 가능한 것으로 표시되지 않는다. 경로 문자열·위장 확장자를 그대로 실행하지 않는다.
- 저장물 백업/복원/삭제, 브라우저 3컨텍스트 동시 시험을 수행한다. 실제 LAN 3PC 검수는 S15에서 반복한다.

## 경계와 인계

S04/S05에는 원본 ID와 camera/파생 관계를 제공한다. INSV 자동 변환기는 기본 제공으로 확약하지 않고 S16 호환성 조사 후 필요 범위를 결정한다. 외부 원격 전송이나 고객 발송 기능은 추가하지 않는다.

### 2026-10-04 구현·검증 기록

`upload_receipts`(DB schema11)에 서버 발급 ID·요청 내용 해시·점유 토큰·수신/실패/완료/연결 상태를 저장한다. 파일 수신은 참가자 연결보다 먼저 끝내며 완료 파일은 불변 경로/bytes/hash로 유지한다. 연결은 현재 회차와 revision을 검증하는 짧은 append 트랜잭션이다. 같은 파일의 반복 연결은 중복 영상을 만들지 않으며 충돌409에서도 완료 파일은 남는다. 같은 카메라의 서로 다른 파일은 별개로 보존한다.

`media_v4.py`와 `SessionV4.videos`가 원본/수령 변환본·부모 hash/ID·도구/버전/설정·camera 원본번호를 보존한다. INSV는 storage_only이며 MP4로 이름을 바꾸어 분석 가능하다고 표시하지 않는다. 카메라 원본번호 기본 매핑은 CAM1=1/CAM2=3/CAM3=2다. D01 잠정 배치와 추가 카메라 식별자는 구분한다. 이전 입력의 카메라 미배정 영상은 원본을 보존하고 S04에서 명시 확인하며 S05에서 임의 배정하지 않는다.

`/api/uploads` 수신·조회·stream·link·download·정리 API와 `UploadInbox.tsx`를 촬영 화면에 연결했다. 운영자/관리자는 공유 보관함을 조회·연결하고 작성자/관리자만 미연결 자료를 정리한다. 연결된 영상은 기존 참가자 읽기 권한의 검수자도 볼 수 있으나 수신함 전체 권한을 열지 않는다. 파일 선택·수신 중단·재시도·재접속·연결 충돌·INSV 보관 상태를 표시한다. 실제 파일 폐기는 offline 유지보수에서 처리하며 임의 자동 보관기간을 도입하지 않았다.

독립 cold review와 통합 검증에서 다음 발견사항을 수용·수정했다.

- 재촬영 회차 선택 후에도 이전 회차의 수신물을 조회할 수 있도록 조회와 현재 회차 쓰기 검사를 분리했다.
- 변환 부모의 DB hash뿐 아니라 실제 파일과 전체 출처 연결을 검증하고, 큰 파일 hash 검사 뒤 권한·삭제·동의·파일 상태를 다시 확인한다.
- 부모를 정리한 실패 수신물은 상태 조회와 정리를 계속 허용하되 수신 완료·연결·다운로드는 막는다.
- 참가자 연결 전 백업에도 현재 삭제된 upload ID/하위 변환본 ID 대장을 재적용한다. 파일명·본문은 삭제 기록에 남기지 않으며 아직 실제 폐기하지 않은 삭제 요청도 반영한다.
- 큰 파일 쓰기·fsync·출처 hash는 비동기 서버를 막지 않도록 thread에서 실행한다. 취소 시 실행 중 thread 종료를 기다린 뒤 부분 파일을 정리하며 완료 응답 유실의 불변 파일은 유지한다.
- 기존 참가자 영상 URL도 새 수신물의 출처·동의 검사를 우회하지 않는다. 보존된 구 입력 영상도 hash 뒤 로그인·동의를 다시 확인한다.
- 브라우저에서 파일 선택 이벤트를 늦게 읽어 대기 목록이 사라지는 문제를 수정했다.

검증: uploads 합성 **23개**, API **5개**, 기존 접수/마이그레이션·Forms·백업/권한 회귀 **45개** 통과. `npm run build` 및 `KDOG_TEST_INTAKE_SPEC=20261002 npx playwright test tests/uploads-v4.spec.ts` **1개(3개 독립 브라우저 컨텍스트)** 통과. 실제 서버에서 세 업로드 완료→같은 revision 연결 1성공/2충돌→파일 재전송 없이 연결 재시도→3개 고유 영상·카메라 매핑→재접속·INSV 보관을 확인했다. 이 시험은 실제 LAN 3PC 및 GB급 영상 실측을 대신하지 않는다.

2026-10-04 [Python 최신 안정판3.14.8](https://www.python.org/downloads/release/python-3148/)과 [asyncio thread/shield API](https://docs.python.org/3/library/asyncio-task.html)를 확인했다. 기존 잠금/실행환경3.14.2를 유지했으며 to_thread(3.9+)/shield 호환을 시험했다. FastAPI/Pydantic/React/Playwright는 [실행 기록](K-DOG_구현실행기록_v1.0_20261003.md)의 공식 확인 버전을 유지했고 새 의존성은 없다. 실제 파일·장비·LAN 실측과 INSV 변환 품질은 [후속 대장](K-DOG_실측및확인후속대장_v1.0_20261003.md)으로 이관한다.
